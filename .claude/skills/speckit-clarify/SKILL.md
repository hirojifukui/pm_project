## ユーザー入力

```text
$ARGUMENTS
```

続行する前に、ユーザー入力を**必ず**考慮すること（空でない場合）。

## 実行前チェック

**拡張フックの確認（明確化の前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_clarify` キー配下のエントリを探す
- YAML がパースできない、または不正な場合は黙ってスキップしない。`.specify/extensions.yml` を読み取れなかったこと（パーサのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めてフックが一切チェックされなかったことをユーザーに伝え、その上で通常どおり続行する
- `enabled` が明示的に `false` のフックを除外する。`enabled` フィールドを持たないフックは既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null／空の場合は、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件の評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```
    上記のブロックを出力した後、実際にそのフックを必ず呼び出し、完了を待ってから続行すること。このエージェント／セッションで自分がそのコマンドを実行する場合と同じ方法で実行する（呼び出し方は上に示した文字どおりの `{command}` ID と異なる場合がある。例えば skills モードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
- フックが1件も登録されていない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## 概略

目的: 有効な機能仕様書の中の曖昧さや欠落した意思決定ポイントを検出して減らし、明確化の結果を仕様書ファイルに直接記録する。

注意: この明確化ワークフローは `/speckit-plan` を呼び出す**前**に実行（かつ完了）されることが想定されている。ユーザーが明確化をスキップすると明示した場合（探索的スパイクなど）は続行してよいが、後工程での手戻りリスクが高まることを必ず警告すること。

実行手順:

1. リポジトリルートから `{SCRIPT}` を**一度だけ**実行する（`--json --paths-only` モード／`-Json -PathsOnly` の組み合わせ）。最小限の JSON ペイロードのフィールドをパースする:
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - （将来の連鎖フローのために `IMPL_PLAN`、`TASKS` を任意で取得しておく。）
   - JSON のパースに失敗した場合は中断し、`/speckit-specify` の再実行、または機能ブランチ環境の確認をユーザーに指示する。
   - "I'm Groot" のように引数内にシングルクォートが含まれる場合は、エスケープ構文を使う: 例 'I'\''m Groot'（可能ならダブルクォートでもよい: "I'm Groot"）。

2. **存在する場合**: プロジェクトの原則とガバナンス上の制約を把握するため `/memory/constitution.md` を読み込む。

3. 現在の仕様書ファイルを読み込む。次の分類体系を用いて、構造化された曖昧さ・網羅性のスキャンを実施する。各カテゴリについて、明確 / 部分的 / 欠落 のいずれかのステータスを付ける。優先順位付けに使う内部的な網羅性マップを作成する（質問を1件も行わない場合を除き、生のマップは出力しない）。

   機能スコープと振る舞い:
   - 中核的なユーザーの目的と成功基準
   - スコープ外であることの明示的な宣言
   - ユーザーのロール／ペルソナの区別

   ドメインとデータモデル:
   - エンティティ、属性、関連
   - 同一性と一意性のルール
   - ライフサイクル／状態遷移
   - データ量／スケールの前提

   インタラクションと UX フロー:
   - 重要なユーザージャーニー／操作手順
   - エラー／空／ローディング状態
   - アクセシビリティまたはローカライズに関する注記

   非機能品質特性:
   - パフォーマンス（レイテンシ、スループットの目標）
   - スケーラビリティ（水平／垂直、上限）
   - 信頼性と可用性（稼働率、復旧に関する期待）
   - オブザーバビリティ（ロギング、メトリクス、トレーシングのシグナル）
   - セキュリティとプライバシー（認証／認可、データ保護、脅威の前提）
   - コンプライアンス／規制上の制約（ある場合）

   統合と外部依存:
   - 外部サービス／API と障害モード
   - データのインポート／エクスポート形式
   - プロトコル／バージョニングの前提

   エッジケースと障害処理:
   - 異常系シナリオ
   - レート制限／スロットリング
   - 競合の解決（例: 同時編集）

   制約とトレードオフ:
   - 技術的制約（言語、ストレージ、ホスティング）
   - 明示的なトレードオフ、または却下した代替案

   用語と一貫性:
   - 正規の用語集の項目
   - 使用を避ける同義語／非推奨用語

   完了のシグナル:
   - 受け入れ基準のテスト可能性
   - 測定可能な Definition of Done 的な指標

   その他／プレースホルダ:
   - TODO マーカー／未解決の意思決定
   - 定量化を欠く曖昧な形容詞（「堅牢」「直感的」など）

   ステータスが 部分的 または 欠落 の各カテゴリについて、次に該当しない限り質問候補を追加する:
   - 明確化しても実装や検証の戦略が実質的に変わらない場合
   - その項目が実装手段、技術スタックの比較、タスク分解に関するものである場合（内部的に記録する）

4. 明確化の質問候補について、優先順位付きのキューを（内部的に）生成する（最大5件）。それらを一度にすべて出力しては**ならない**。次の制約を適用する:
    - セッション全体を通じて合計で最大5件の質問。
    - 各質問は次のいずれかで回答可能であること:
       - 短い選択式（2〜5個の、明確に区別され相互排他な選択肢）、または
       - 単語1語／短いフレーズでの回答（明示的に制約する: 「5語以内で回答」）。
    - 回答がアーキテクチャ、データモデリング、タスク分解、テスト設計、UX の振る舞い、運用準備、またはコンプライアンス検証に実質的な影響を与える質問のみを含める。
    - カテゴリ網羅のバランスを確保する: 影響度が最も高い未解決カテゴリから先に扱うよう努める。影響度の高い領域（例: セキュリティ体制）が未解決のまま、影響度の低い質問を2件するようなことは避ける。
    - すでに回答済みの質問、些末なスタイルの好み、計画レベルの実行詳細は除外する（正しさをブロックする場合を除く）。
    - 後工程での手戻りリスクを減らす、または受け入れテストのズレを防ぐ明確化を優先する。
    - 未解決カテゴリが5件を超える場合は、（影響度 × 不確実性）のヒューリスティックで上位5件を選ぶ。

5. 逐次質問ループ（対話的）:
    - 一度に**ちょうど1件**の質問を提示する。
    - **質問の記述品質（選択式・短答式を問わず、すべての質問に適用）:**
       - 先頭を `**質問:**` とし、その後に `?` で終わる完全な疑問文を続ける。`?` より前の質問文は、それ単独で意味が通らなければならない。
       - トピックのラベル、セクション見出し、要件 ID を質問そのものとして使っては**絶対にならない**。例えば `受け入れ用デバイス／ランタイムのマトリクス (FR-023)` は**不正**である — これはラベルであって質問ではない。
       - `?` の後に置いてよいのは、括弧書きの要件 ID／質問 ID のみである。厳密な形式は次のとおり: `**質問:** <疑問文>?` または `**質問:** <疑問文>? (FR-023)`。ID を `?` より前に置いてはならず、ID を（単独でも、トピックのラベルと組み合わせても）プロンプト全体として使ってはならない。
       - 質問行の直後に、推奨／選択肢の前として、平易な言葉で「なぜ重要か」を述べる文を1文追加する（受け入れやリリースにとっての利害）。
       - 日常的な言葉遣いを使い、専門用語は同じ文の中で定義する場合にのみ導入する。セルフチェック: Spec Kit を知らない読者が、質問行だけを読んで回答できなければならない。簡潔なのは構わないが、暗号めいたラベルは不可。
    - 選択式の質問の場合:
       - **すべての選択肢を分析**し、次の観点に基づいて**最も適した選択肢**を判断する:
          - そのプロジェクト種別におけるベストプラクティス
          - 類似実装でよく使われるパターン
          - リスク低減（セキュリティ、パフォーマンス、保守性）
          - 仕様書から読み取れる明示的なプロジェクト目標や制約との整合
       - **推奨する選択肢を目立つ形で**先頭に提示し、明確な理由を添える（なぜそれが最善かを説明する1〜2文）。
       - 形式は次のとおり: `**推奨:** 選択肢 [X] - <理由>`
       - 続いて、すべての選択肢を Markdown の表として描画する:

       | 選択肢 | 説明 |
       |--------|-------------|
       | A | <選択肢 A の説明> |
       | B | <選択肢 B の説明> |
       | C | <選択肢 C の説明>（必要に応じて最大5件まで D/E を追加） |
       | Short | 別の短い回答を記入する（5語以内）（自由記述の代替が適切な場合のみ含める） |

       - 表の後に次を追加する: `選択肢の記号（例: 「A」）で回答するか、「yes」または「recommended」と答えて推奨を採用するか、独自の短い回答を提示できます。`
    - 短答式（意味のある離散的な選択肢がない場合）:
       - ベストプラクティスと文脈に基づいて**提案する回答**を示す。
       - 形式は次のとおり: `**提案:** <提案する回答> - <簡潔な理由>`
       - 続いて次を出力する: `形式: 短答（5語以内）。「yes」または「suggested」と答えて提案を採用するか、独自の回答を提示できます。`
    - ユーザーの回答後:
       - ユーザーが「yes」「recommended」「suggested」と答えた場合は、直前に提示した推奨／提案を回答として採用する。
       - それ以外の場合は、回答がいずれかの選択肢に対応するか、5語以内の制約に収まるかを検証する。
       - 曖昧な場合は、手短に曖昧さの解消を求める（カウントは同じ質問に属したままで、次へ進まない）。
       - 満足のいく回答が得られたら、作業メモリに記録し（この時点ではまだディスクに書き込まない）、キューの次の質問へ進む。
    - 次の場合は、それ以上質問するのをやめる:
       - 重要な曖昧さが早期にすべて解消された場合（キューに残った項目が不要になる）、または
       - ユーザーが完了を示した場合（「done」「good」「no more」）、または
       - 質問数が5件に達した場合。
    - キューに残っている今後の質問を事前に明かしては絶対にならない。
    - 開始時点で有効な質問が1件も存在しない場合は、重要な曖昧さがない旨を直ちに報告する。

6. 回答を受理する**たび**に行う統合（逐次更新方式）:
    - 仕様書のインメモリ表現（開始時に一度読み込んだもの）と生のファイル内容の両方を保持する。
    - このセッションで最初に統合する回答の場合:
       - `## Clarifications` セクションが存在することを確認する（なければ、仕様書テンプレートに従って最上位の文脈／概要セクションの直後に作成する）。
       - その配下に、今日の日付の `### Session YYYY-MM-DD` という小見出しを作成する（まだない場合）。
    - 受理した直後に箇条書き行を追記する: `- Q: <質問> → A: <最終的な回答>`。
    - 続いて直ちに、その明確化を最も適切なセクションへ反映する:
       - 機能面の曖昧さ → 機能要件の箇条書きを更新または追加する。
       - ユーザー操作／アクターの区別 → ユーザーストーリー、またはアクターの小セクション（存在する場合）を、明確化されたロール・制約・シナリオで更新する。
       - データ構造／エンティティ → データモデルを更新し（フィールド、型、関連を追加）、順序を保つ。追加された制約は簡潔に注記する。
       - 非機能的な制約 → 成功基準 > 測定可能な成果に測定可能な基準を追加／修正する（曖昧な形容詞を指標または明示的な目標値へ変換する）。
       - エッジケース／異常系フロー → エッジケース／エラー処理の配下に新しい箇条書きを追加する（テンプレートにその小セクションのプレースホルダがある場合は作成する）。
       - 用語の衝突 → 仕様書全体で用語を統一する。必要な場合に限り、`(formerly referred to as "X")` を一度だけ追加して元の用語を残す。
    - 明確化によって以前の曖昧な記述が無効になる場合は、重複させずにその記述を置き換える。陳腐化した矛盾するテキストを残さないこと。
    - コンテキスト消失のリスクを最小化するため、統合のたびに仕様書ファイルを保存する（アトミックな上書き）。
    - 書式を保つ: 無関係なセクションを並べ替えない。見出し階層をそのまま維持する。
    - 挿入する明確化は、最小限かつテスト可能に保つ（記述が物語的に膨らまないようにする）。

7. 検証（書き込みの**たび**に加えて、最終パスでも実施）:
   - Clarifications のセッションに、受理した回答ごとにちょうど1つの箇条書きがある（重複がない）。
   - 質問した（受理した）合計件数が 5 件以下である。
   - 更新したセクションに、新しい回答で解消されるはずだった曖昧なプレースホルダが残っていない。
   - 矛盾する以前の記述が残っていない（無効になった代替案が削除されているかスキャンする）。
   - Markdown 構造が正しい。新たに許可される見出しは `## Clarifications` と `### Session YYYY-MM-DD` のみ。
   - 用語の一貫性: 更新したすべてのセクションで同じ正規用語が使われている。

8. 更新した仕様書を `FEATURE_SPEC` へ書き戻す。

9. **仕様書品質チェックリストの再検証**（存在する場合）:
   - `FEATURE_DIR/checklists/requirements.md` が存在するか確認する。
   - 存在**しない**場合は、この手順を黙ってスキップする。
   - 存在する場合:
     1. チェックリストファイルを読み込む。
     2. GitHub のタスクリスト形式のチェックボックス行をすべて特定する — コードフェンスの外にある `- [ ]`、`- [x]`、`- [X]` にマッチする行（大文字小文字を区別せず、入れ子項目の先頭空白を許容する）。それ以外の内容（見出し、注記、チェックボックスでない箇条書き、メタデータ）はすべて無視する。
     3. 各チェックボックス行について、現在のマーカー状態（チェック済みか未チェックか）と項目テキストを、変更前スナップショットのリストに記録する。
     4. **更新後**の仕様書（手順7で保存したばかりの版）に対して、各チェックボックス項目を再評価する。
     5. 各チェックボックス項目について、チェック済み／未チェックの状態が実際に変化した場合のみ更新する:
        - 項目が合格するようになり、以前は未チェックだった場合: `[ ]` を `[x]` に変更する。
        - 項目が不合格になり、以前はチェック済みだった場合: `[x]`／`[X]` を `[ ]` に変更する。
        - 状態が変化していない場合: マーカーをそのままにする（見た目だけの差分を避けるため既存の大文字小文字を保つ）。
     6. 更新したチェックリストファイルを保存する。**状態が変化したチェックボックス行の `[ ]`／`[x]` マーカー部分のみを切り替えること。** その他のファイル内容 — 見出し、メタデータ、注記、行の並び順、空白 — は、ノイズの多い差分を避けるためすべて変更してはならない。
     7. 変更前スナップショットと現在の状態を比較し、完了報告用に次の3つのリストを算出する:
        - **新たに合格**: 未チェックからチェック済みへ変化した項目。
        - **リグレッション**: チェック済みから未チェックへ変化した項目。
        - **依然として未チェック**: 未チェックのままの項目。
     8. 変更前／変更後の合格数を、チェック済み数／チェックボックス総数として記録する（例: 「12/16 → 15/16 項目が合格」）。

振る舞いのルール:

- 意味のある曖昧さが見つからない場合（または想定されるすべての質問が低影響である場合）、次のように応答する: 「正式な明確化に値する重要な曖昧さは検出されませんでした。」そのうえで先に進むことを提案する。
- 仕様書ファイルが存在しない場合は、先に `/speckit-specify` を実行するようユーザーに指示する（ここで新しい仕様書を作成しないこと）。
- 質問の合計件数が5件を超えては絶対にならない（1つの質問に対する明確化のやり直しは新しい質問として数えない）。
- 機能面の明確さがブロックされる場合を除き、投機的な技術スタックの質問は避ける。
- ユーザーの早期終了のシグナル（「stop」「done」「proceed」）を尊重する。
- 網羅性が十分で質問を1件も行わなかった場合は、コンパクトな網羅性サマリ（全カテゴリが 明確）を出力してから、次へ進むことを提案する。
- 上限件数に達してもなお影響度の高いカテゴリが未解決で残っている場合は、それらを 先送り として理由とともに明示的に示す。

優先順位付けのためのコンテキスト: {ARGS}

## 必須の実行後フック

**ユーザーに完了を報告する前に、このセクションを必ず完了させること。**

プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在しない場合、または `hooks.after_clarify` 配下にフックが登録されていない場合は、完了報告へ進む。
- 存在する場合は読み込み、`hooks.after_clarify` キー配下のエントリを探す。
- YAML がパースできない、または不正な場合は黙ってスキップしない。`.specify/extensions.yml` を読み取れなかったこと（パーサのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めてフックが一切チェックされなかったことをユーザーに伝え、その上で完了報告へ進む。
- `enabled` が明示的に `false` のフックを除外する。`enabled` フィールドを持たないフックは既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null／空の場合は、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件の評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **必須フック**（`optional: false`） — **必須フックごとに `EXECUTE_COMMAND:` を必ず出力すること**:
    ```
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    上記のブロックを出力した後、実際にそのフックを必ず呼び出し、完了を待ってから続行すること。このエージェント／セッションで自分がそのコマンドを実行する場合と同じ方法で実行する（呼び出し方は上に示した文字どおりの `{command}` ID と異なる場合がある。例えば skills モードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
  - **任意フック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

## 完了報告

完了を報告する（質問ループの終了後、または早期終了後）:
- 質問し回答を得た件数。
- 更新した仕様書のパス。
- 変更したセクション（名称を列挙）。
- 仕様書品質チェックリストの状況（`FEATURE_DIR/checklists/requirements.md` を再検証した場合）: 変更前／変更後の合格数を示し（例: 「仕様書品質チェックリスト: 12/16 → 15/16 項目が合格」）、状態が変化した項目 — 新たにチェックされたもの（未チェック → チェック済み）と、リグレッション（チェック済み → 未チェック）の両方 — を列挙する。未チェックのまま残る項目があれば、注意が必要な箇所として列挙する。
- 網羅性サマリの表。分類体系の各カテゴリについて、次のステータスを記載する: 解決済み（部分的／欠落だったが対応した）、先送り（質問の上限を超えた、または残った項目が実装手段・技術スタックの比較・タスク分解に関するものである）、明確（すでに十分）、未解決（依然として 部分的／欠落 だが影響度が低い）。
- 未解決 または 先送り が残っている場合は、`/speckit-plan` へ進むべきか、計画後に改めて `/speckit-clarify` を実行すべきかを推奨する。
- 推奨する次のコマンド。

## 完了条件

- [ ] 仕様書の曖昧さを特定し、明確化の結果を仕様書ファイルへ統合した
- [ ] 更新後の仕様書に対して仕様書品質チェックリストを再検証した（`FEATURE_DIR/checklists/requirements.md` が存在する場合）
- [ ] 上記「必須の実行後フック」のルールに従って拡張フックをディスパッチまたはスキップした
- [ ] 回答した質問、変更したセクション、チェックリストの状況、網羅性サマリを含めてユーザーへ完了を報告した

## 業務分析拡張（Spec Kit 日本語版）

このセクションは、業務システムの要件分析を補強するために Spec Kit 日本語版が追加した規約である。仕様書に `## 業務要件` セクションがある場合に適用する。無い場合は本セクションを無視する。

### B1. 追加の分類カテゴリ

実行手順3の分類体系に、次のカテゴリを加えて評価する。

業務ルールと権限:
- 業務ルール（BR-###）の数値・条件・対象者が具体的か（上限額、期限、対象となる役職など）
- ロールごとの操作権限（自分の申請と他人の申請、代理、兼務、同一人物が複数ロールを持つ場合）
- 業務上の例外（EX-###）で、誰が判断し、どう処理するかが決まっているか
- ルールの根拠が慣習だけのもの（前提 に「慣習のため要確認」とあるもの）を、正式なルールとして扱うか
- 前提 に「（Q-xx、要確認）」として残っている未確定事項

「（Q-xx、要確認）」と「慣習のため要確認」の項目は、影響度が同程度なら他のカテゴリより優先して質問候補にする。

### B2. 統合先の追加

実行手順6の統合先に、次を加える。

- 業務ルールの明確化 → `### 業務ルール` の BR-### を更新または追加する。既存の BR を更新した場合は出典に追記する（例: `出典: R-05、Q-04 clarify YYYY-MM-DD`）。新しく追加した BR の出典は `出典: clarify YYYY-MM-DD` とする。
- 権限の明確化 → `### 権限（ロールと操作）` の表を更新する。ロール名を変えた場合は、ユーザーストーリーのアクター名もそろえる。
- 業務上の例外の明確化 → `### 業務上の例外処理` の EX-### を更新または追加し、必要ならエッジケースにも反映する。
- 用語の衝突 → `### 用語集` を更新する。
- 前提 にある「（Q-xx、要確認）」「慣習のため要確認」が解決した場合 → 「要確認」の注記を外す。扱うと決まった内容は BR-### / EX-### へ反映し、前提 からは削除する。扱わないと決まった内容は、その決定と出典 ID を 前提 に残す（ヒアリングシートの行との対応を失わないため）。

実行手順7の「新たに許可される見出し」の制約は変わらない。`## 業務要件` とその小見出し（権限、業務ルール、業務上の例外処理、用語集）はテンプレート由来の見出しとして扱い、specify が削除していた場合でも、回答の反映に必要なら復元してよい。

### B3. 質問の言葉遣い

回答者は業務担当者（プログラミング経験のない人）であることを前提にする。

- 「ロール」「エンティティ」「ステータス遷移」などの言葉は使わず、「誰が」「どの書類で」「どの段階で」と聞く。
- 選択肢は、業務の場面で起きることとして書く。例: 「A: 所属長が不在の間は、部長が代わりに承認する」
- 数値を聞く場合は、単位を明記する（円、日、件）。

### B4. ヒアリングシートの扱い

- ヒアリングシートは聞き取り時点の記録として残し、このコマンドでは書き換えない。
- 完了報告に「解決したヒアリングシートの未確定事項（Q-xx）」の一覧を加え、ヒアリングシート側の更新はユーザーに委ねる。

## 日本語出力ガードレール（Spec Kit 日本語版 / 全コマンド共通）

このセクションは Spec Kit 日本語版が全コマンドに付与する共通の後処理規約である。**省略してはならない。**

### G1. 成果物の記述言語

このコマンドがファイルを生成・更新する場合（`spec.md` / `plan.md` / `tasks.md` / `checklists/*.md` / `.specify/memory/constitution.md` / `research.md` / `data-model.md` / `quickstart.md` / `contracts/` 配下など）、その本文は**日本語**で記述すること。ユーザーへのチャット応答も日本語で行う。

次のものは例外として**英語のまま**維持する。

- ソースコード、シェルコマンド、識別子、型名、ファイルパス、ディレクトリ名、ブランチ名
- `[NEEDS CLARIFICATION: ...]`、`[P]`、`FR-###`、`SC-###`、`NFR-###`、`US1`/`US2`/`US3`、`T001` などの機械可読マーカーおよびID書式
- 業務分析拡張の ID 書式（`BR-###`、`EX-###`）と、ヒアリングシートの ID 書式（`AS-01`、`TB-01`、`R-01`、`E-01`、`Q-01`）
- `**Given**` / `**When**` / `**Then**`（Gherkin 記法）
- 外部ツールやこのコマンド自身が解釈する固定文字列（`EXECUTE_COMMAND:` など）
- 技術用語の原語表記が適切な場合の英単語（API、CI、OAuth など）

ユーザーが英語で指示した場合や、既存の成果物が英語で書かれている場合は、その言語に合わせてよい。それ以外は日本語を既定とする。

### G2. 文字化け検証（書き込み後に必ず実行）

ファイルの書き込み・編集が完了したら、**毎回**次の手順を実行する。

1. 書き込んだファイルを読み直す。
2. 次のいずれかに該当しないか確認する。
   - 置換文字 U+FFFD（いわゆる「黒ひし形に疑問符」の記号）が含まれる
   - mojibake パターンが含まれる（`ã`, `â`, `ï¿½`, `ãƒ`, `æ–‡`, `ð` で始まる不自然な連なりなど）
   - 日本語で書くべき本文が英語のままになっている（G1 の例外を除く）
   - 見出しや表が壊れている（列数の不一致、閉じていないコードフェンス）
3. 該当した場合は、そのファイルを **UTF-8 (BOMなし)** で**丸ごと書き直す**。差分パッチや部分置換で済ませない。
4. 書き直しを2回試しても解消しない場合は、作業を中断し、ユーザーに次を報告する。

   > 文字化けが解消しません。エディタまたは端末のエンコーディング設定（UTF-8 / コードページ）を確認してください。Windows PowerShell の場合は `$PSDefaultParameterValues['*:Encoding']='utf8'` と `chcp 65001` を確認してください。

### G3. 用語の統一

同一プロジェクト内では訳語を揺らさない。既に `spec.md` や `constitution.md` で使われている訳語があれば、それに合わせる。判断に迷う場合は英語を併記する（例: 受け入れシナリオ (acceptance scenario)）。
