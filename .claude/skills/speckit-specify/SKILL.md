## ユーザー入力

```text
$ARGUMENTS
```

続行する前に、ユーザー入力を（空でない限り）**必ず**考慮すること。

## 実行前チェック

**拡張フックの確認（仕様書作成の前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合はそれを読み込み、`hooks.before_specify` キー配下のエントリを探す
- YAML がパースできない、または不正な場合は、黙ってスキップしないこと: `.specify/extensions.yml` を読めなかったこと（パーサーのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含め、フックが一切チェックされなかったことをユーザーに伝え、その後は通常どおり続行する
- `enabled` が明示的に `false` のフックは除外する。`enabled` フィールドを持たないフックは既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈または評価しようとしては**ならない**:
  - フックに `condition` フィールドが無い、または null／空の場合は、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件の評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```
    上記のブロックを出力した後、実際にフックを呼び出し、続行する前にその完了を必ず待つこと。この エージェント／セッション で自分がそのコマンドを実行するのと同じ方法で実行する（呼び出し方は上に示した `{command}` の ID そのものとは異なる場合がある。例えば skills モードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
- フックが1つも登録されていない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## アウトライン

トリガーとなったメッセージ内で `/speckit-specify` の後にユーザーが入力したテキスト**こそが**機能説明である。以下に `{ARGS}` が文字どおり現れていても、この会話の中で常にそれが利用可能だと想定すること。ユーザーが空のコマンドを渡した場合を除き、入力し直すよう求めてはならない。

その機能説明を前提に、以下を実行する:

1. 機能の**簡潔なショートネームを生成する**（2〜4語）:
   - 機能説明を分析し、最も意味のあるキーワードを抽出する
   - 機能の本質を捉えた2〜4語のショートネームを作る
   - 可能な場合は「動作-名詞」形式を用いる（例: "add-user-auth", "fix-payment-bug"）
   - 技術用語や略語は保持する（OAuth2, API, JWT など）
   - 簡潔さを保ちつつ、一目で機能が分かる程度に説明的にする
   - 例:
     - "I want to add user authentication" → "user-auth"
     - "Implement OAuth2 integration for the API" → "oauth2-api-integration"
     - "Create a dashboard for analytics" → "analytics-dashboard"
     - "Fix payment processing timeout bug" → "fix-payment-timeout"

2. **ブランチ作成**（任意、フック経由）:

   上の実行前チェックで `before_specify` フックが正常に実行された場合、そのフックが git ブランチを作成／切り替えし、`BRANCH_NAME` と `FEATURE_NUM` を含む JSON を出力している。これらの値は参考として控えておくが、ブランチ名が仕様ディレクトリ名を決めるわけでは**ない**。

   ユーザーが `GIT_BRANCH_NAME` を明示的に指定した場合は、それをそのままフックに渡し、ブランチスクリプトがその値をブランチ名としてそのまま使うようにする（接頭辞・接尾辞の生成はすべてバイパスする）。

3. **仕様の機能ディレクトリを作成する**:

   ユーザーが `SPECIFY_FEATURE_DIRECTORY` を明示的に指定しない限り、仕様書は既定の `specs/` ディレクトリ配下に置く。

   **`SPECIFY_FEATURE_DIRECTORY` の解決順序**:
   1. ユーザーが `SPECIFY_FEATURE_DIRECTORY` を明示的に指定した場合（環境変数、引数、設定などを通じて）は、それをそのまま使う
   2. そうでない場合は、`specs/` 配下に自動生成する:
      - `.specify/init-options.json` の `feature_numbering`（推奨）または `branch_numbering`（非推奨、移行用のみ — 将来のリリースで削除予定）を確認する
      - `"timestamp"` の場合: 接頭辞は `YYYYMMDD-HHMMSS`（現在のタイムスタンプ）
      - `"sequential"` または未指定の場合: 接頭辞は `NNN`（`specs/` 内の既存ディレクトリを走査した上で次に使える3桁の番号）
      - ディレクトリ名を組み立てる: `<prefix>-<short-name>`（例: `003-user-auth` や `20260319-143022-user-auth`）
      - `SPECIFY_FEATURE_DIRECTORY` を `specs/<directory-name>` に設定する
      - `branch_numbering` が使われた場合（かつ `feature_numbering` が無かった場合）は、1行の警告を出力する: 「⚠️ init-options.json の `branch_numbering` は非推奨である。`feature_numbering` に改名すること。」

   **ディレクトリと仕様ファイルを作成する**:
   - `mkdir -p SPECIFY_FEATURE_DIRECTORY`
   - Spec Kit のプリセット／テンプレート解決スタックを通じて、有効な `spec-template` を解決する（`specify preset resolve spec-template` と同等）
   - 解決された `spec-template` ファイルを出発点として `SPECIFY_FEATURE_DIRECTORY/spec.md` にコピーする
   - `SPEC_FILE` を `SPECIFY_FEATURE_DIRECTORY/spec.md` に設定する
   - 解決されたパスを `.specify/feature.json` に永続化する:
     ```json
     {
       "feature_directory": "<resolved feature dir>"
     }
     ```
     リテラル文字列 `SPECIFY_FEATURE_DIRECTORY` ではなく、実際に解決されたディレクトリパスの値（例: `specs/003-user-auth`）を書き込むこと。
     これにより、下流のコマンド（`/speckit-plan`、`/speckit-tasks` など）が git のブランチ名の慣習に依存せずに機能ディレクトリを特定できる。

   **重要**:
   - `/speckit-specify` の1回の呼び出しで作成してよい機能は1つだけである
   - 仕様ディレクトリ名と git のブランチ名は独立している — 同じにしてもよいが、それはユーザーの選択である
   - 仕様ディレクトリとファイルは常にこのコマンドが作成し、フックが作成することは決してない

4. 必要なセクションを把握するため、解決された有効な `spec-template` ファイルを読み込む。

5. **存在する場合**: プロジェクトの原則とガバナンス上の制約を把握するため、`/memory/constitution.md` を読み込む。

6. 次の実行フローに従う:
    1. 引数からユーザーの説明をパースする
       空の場合: ERROR "No feature description provided"
    2. 説明から主要な概念を抽出する
       特定する対象: アクター、アクション、データ、制約
    3. 不明瞭な点について:
       - コンテキストと業界標準に基づいて、根拠のある推測を行う
       - 次の場合に限り [NEEDS CLARIFICATION: specific question] でマークする:
         - その選択が機能のスコープやユーザー体験に大きく影響する
         - 影響の異なる複数の妥当な解釈が存在する
         - 妥当な既定値が存在しない
       - **上限: [NEEDS CLARIFICATION] マーカーは合計で最大3個**
       - 明確化は影響度の順に優先する: スコープ > セキュリティ／プライバシー > ユーザー体験 > 技術的詳細
    4. ユーザーシナリオとテスト セクションを埋める
       明確なユーザーフローが無い場合: ERROR "Cannot determine user scenarios"
    5. 機能要件 を生成する
       各要件はテスト可能でなければならない
       明示されていない詳細には妥当な既定値を使う（前提は 前提 セクションに記録する）
    6. 成功基準 を定義する
       測定可能で、技術に依存しない成果を作成する
       定量的な指標（時間、性能、量）と定性的な尺度（ユーザー満足度、タスク完了）の両方を含める
       各基準は実装の詳細なしに検証可能でなければならない
    7. 主要エンティティ を特定する（データを扱う場合）
    8. 返す: SUCCESS (spec ready for planning)

7. テンプレートの構造を用いて仕様書を SPEC_FILE に書き込む。セクションの順序と見出しは保ったまま、プレースホルダを機能説明（引数）から導かれる具体的な内容に置き換える。

8. **仕様書の品質検証**: 初版の仕様書を書き終えたら、品質基準に照らして検証する:

   a. **仕様品質チェックリストを作成する**: チェックリストテンプレートの構造を用い、次の検証項目を含むチェックリストファイルを `SPECIFY_FEATURE_DIRECTORY/checklists/requirements.md` に生成する:

      ```markdown
      # 仕様品質チェックリスト: [機能名]

      **目的**: 計画フェーズへ進む前に、仕様書の完全性と品質を検証する
      **作成日**: [DATE]
      **機能**: [Link to spec.md]

      ## 内容の品質

      - [ ] 実装の詳細（言語、フレームワーク、API）が含まれていない
      - [ ] ユーザー価値とビジネスニーズに焦点が当たっている
      - [ ] 技術者でないステークホルダー向けに書かれている
      - [ ] 必須セクションがすべて記入されている

      ## 要件の網羅性

      - [ ] [NEEDS CLARIFICATION] マーカーが残っていない
      - [ ] 要件がテスト可能かつ曖昧でない
      - [ ] 成功基準が測定可能である
      - [ ] 成功基準が技術に依存しない（実装の詳細を含まない）
      - [ ] すべての受け入れシナリオが定義されている
      - [ ] エッジケースが特定されている
      - [ ] スコープが明確に限定されている
      - [ ] 依存関係と前提が特定されている

      ## 機能の準備状況

      - [ ] すべての機能要件に明確な受け入れ基準がある
      - [ ] ユーザーシナリオが主要なフローを網羅している
      - [ ] 機能が 成功基準 で定義された測定可能な成果を満たしている
      - [ ] 実装の詳細が仕様書に漏れ出していない

      ## 補足

      - 未完了としてマークされた項目は、`/speckit-clarify` または `/speckit-plan` の前に仕様書の更新を要する
      ```

   b. **検証チェックを実行する**: チェックリストの各項目に照らして仕様書をレビューする:
      - 各項目について、合格か不合格かを判定する
      - 見つかった具体的な問題を記録する（該当する仕様書のセクションを引用する）

   c. **検証結果を処理する**:

      - **すべての項目が合格した場合**: チェックリストを完了としてマークし、必須の実行後フック セクションへ進む

      - **不合格の項目がある場合（[NEEDS CLARIFICATION] を除く）**:
        1. 不合格の項目と具体的な問題を列挙する
        2. 各問題に対処するよう仕様書を更新する
        3. すべての項目が合格するまで検証を再実行する（最大3回）
        4. 3回繰り返しても不合格が残る場合は、残る問題をチェックリストの補足に記録し、ユーザーに警告する

      - **[NEEDS CLARIFICATION] マーカーが残っている場合**:
        1. 仕様書からすべての [NEEDS CLARIFICATION: ...] マーカーを抽出する
        2. **上限チェック**: マーカーが3個を超える場合は、最も重要な3個（スコープ／セキュリティ／UX への影響で判断）だけを残し、残りは根拠のある推測で埋める
        3. 必要な明確化ごとに（最大3個）、次の形式でユーザーに選択肢を提示する:

           ```markdown
           ## 質問 [N]: [トピック]

           **コンテキスト**: [Quote relevant spec section]

           **確認したいこと**: [Specific question from NEEDS CLARIFICATION marker]

           **回答候補**:

           | 選択肢 | 回答 | 影響 |
           |--------|--------|--------------|
           | A      | [First suggested answer] | [What this means for the feature] |
           | B      | [Second suggested answer] | [What this means for the feature] |
           | C      | [Third suggested answer] | [What this means for the feature] |
           | Custom | 自分で回答を入力する | [Explain how to provide custom input] |

           **あなたの選択**: _[Wait for user response]_
           ```

        4. **極めて重要 — 表の書式**: markdown の表が正しく整形されていることを確認する:
           - パイプを揃え、一貫した空白を使う
           - 各セルは内容の前後に空白を入れる: `|Content|` ではなく `| Content |`
           - ヘッダー区切り行はダッシュを3つ以上にする: `|--------|`
           - markdown プレビューで表が正しく描画されることを確認する
        5. 質問には連番を振る（Q1, Q2, Q3 — 合計最大3個）
        6. すべての質問をまとめて提示してから、回答を待つ
        7. すべての質問に対するユーザーの選択を待つ（例: "Q1: A, Q2: Custom - [details], Q3: B"）
        8. 各 [NEEDS CLARIFICATION] マーカーを、ユーザーが選択または提示した回答に置き換えて仕様書を更新する
        9. すべての明確化が解決したら、検証を再実行する

   d. **チェックリストを更新する**: 検証の各回の後、現在の合否状況でチェックリストファイルを更新する

## 完了報告

次の内容をユーザーに報告する:
- `SPECIFY_FEATURE_DIRECTORY` — 機能ディレクトリのパス
- `SPEC_FILE` — 仕様ファイルのパス
- チェックリスト結果の要約
- 次フェーズ（`/speckit-clarify` または `/speckit-plan`）への準備状況

**注意:** ブランチ作成は `before_specify` フック（git 拡張）が担当する。仕様ディレクトリとファイルの作成は、常にこのコアコマンドが担当する。

## クイックガイドライン

- ユーザーが**何を**必要とし、**なぜ**必要とするのかに焦点を当てる。
- どう実装するかは避ける（技術スタック、API、コード構成に触れない）。
- 開発者ではなく、ビジネス側のステークホルダー向けに書く。
- 仕様書に埋め込む形のチェックリストは一切作成しない。それは別のコマンドで行う。

### セクション要件

- **必須セクション**: すべての機能で記入しなければならない
- **任意セクション**: その機能に関係する場合のみ含める
- セクションが当てはまらない場合は、丸ごと削除する（"N/A" として残さない）

### AI による生成について

ユーザーのプロンプトからこの仕様書を作成するときは:

1. **根拠のある推測を行う**: コンテキスト、業界標準、一般的なパターンを使って欠落を埋める
2. **前提を記録する**: 妥当な既定値を 前提 セクションに記録する
3. **明確化を制限する**: [NEEDS CLARIFICATION] マーカーは最大3個 — 次に該当する重要な判断にのみ使う:
   - 機能のスコープやユーザー体験に大きく影響する
   - 影響の異なる複数の妥当な解釈がある
   - 妥当な既定値がまったく無い
4. **明確化を優先順位づけする**: スコープ > セキュリティ／プライバシー > ユーザー体験 > 技術的詳細
5. **テスターのように考える**: 曖昧な要件はすべて「テスト可能かつ曖昧でない」というチェック項目に不合格となるはずである
6. **明確化が必要になりやすい領域**（妥当な既定値が存在しない場合のみ）:
   - 機能のスコープと境界（特定のユースケースを含める／除外する）
   - ユーザー種別と権限（相反する解釈が複数あり得る場合）
   - セキュリティ／コンプライアンス要件（法務的・金銭的に重大な場合）

**妥当な既定値の例**（これらについては質問しない）:

- データ保持: その領域における業界標準の慣行
- 性能目標: 特に指定がなければ、一般的な Web／モバイルアプリの期待水準
- エラー処理: 適切なフォールバックを伴うユーザーフレンドリーなメッセージ
- 認証方式: Web アプリでは標準的なセッションベースまたは OAuth2
- 統合パターン: プロジェクトに適したパターンを使う（Web サービスなら REST/GraphQL、ライブラリなら関数呼び出し、ツールなら CLI 引数など）

### 成功基準のガイドライン

成功基準は次を満たさなければならない:

1. **測定可能**: 具体的な指標（時間、割合、件数、比率）を含む
2. **技術に依存しない**: フレームワーク、言語、データベース、ツールに言及しない
3. **ユーザー中心**: システム内部ではなく、ユーザー／ビジネスの視点から成果を記述する
4. **検証可能**: 実装の詳細を知らなくてもテスト／検証できる

**良い例**:

- 「ユーザーは3分以内にチェックアウトを完了できる」
- 「システムは10,000人の同時ユーザーをサポートする」
- 「検索の95%が1秒以内に結果を返す」
- 「タスク完了率が40%向上する」

**悪い例**（実装に寄っている）:

- 「API のレスポンスタイムが200ms未満」（技術的すぎる。「ユーザーは即座に結果を見られる」を使う）
- 「データベースが1000 TPS を処理できる」（実装の詳細。ユーザーから見た指標を使う）
- 「React コンポーネントが効率的に描画される」（フレームワーク固有）
- 「Redis のキャッシュヒット率が80%以上」（技術固有）

- [ ] 上記の 必須の実行後フック のルールに従って、拡張フックをディスパッチまたはスキップした

## 業務分析拡張（Spec Kit 日本語版）

このセクションは、業務システムの要件分析を補強するために Spec Kit 日本語版が追加した規約である。上記のアウトラインに**追加して**適用する。上記の手順を省略してよい根拠にはしない。

### B1. ヒアリングシートの読み込み

- 機能説明に、ヒアリングシート（`.specify/templates/hearing-sheet-template.md` の構造に沿った Markdown。通常は `docs/requirements/` 配下）のパスが含まれる場合は、アウトラインの手順6の前にそれを読み込み、機能説明の一次情報として扱う。
- パスが無い場合でも、`docs/requirements/` にヒアリングシートが1つだけあり、その業務名が機能説明と一致するときは、それを使ってよい。候補が複数ある場合は推測せず、どれを使うかユーザーに確認する。
- 機能説明とヒアリングシートが矛盾する場合は、どちらかを黙って採用せず、`[NEEDS CLARIFICATION]` の候補として扱う。
- ヒアリングシートは読むだけで、書き換えない。

### B2. 仕様書への対応付け

ヒアリングシートの内容は、次の対応で仕様書（SPEC_FILE）に反映する（ヒアリングシート14章の対応表と同じ）。

| このシートの章 | 仕様書（spec.md）の反映先 |
|----------------|---------------------------|
| 1-1、1-2 目的と背景 | ユーザーストーリーの「この優先度の理由」 |
| 1-3 スコープ外 | 前提 |
| 2 関係者と役割 | ユーザーストーリーのアクター、業務要件 > 権限 |
| 3 As-Is の「困っていること」 | ユーザーストーリーの優先度、成功基準 |
| 4 To-Be 業務フロー（TB-xx） | ユーザーストーリーと受け入れシナリオ |
| 5 業務ルール（R-xx） | 業務要件 > 業務ルール（BR-###）、機能要件 |
| 6 例外（E-xx） | 業務要件 > 業務上の例外処理（EX-###）、エッジケース |
| 7 扱う情報 | 主要エンティティ |
| 8 権限 | 業務要件 > 権限 |
| 9 量・頻度・時期 | 前提、成功基準 |
| 10 外部とのつながり | 前提（依存関係）、機能要件 |
| 11 用語集 | 業務要件 > 用語集 |
| 12 成功の目安 | 成功基準（SC-###） |
| 13 未確定事項（Q-xx） | `[NEEDS CLARIFICATION]`（最大3件）、残りは 前提 |

### B3. 追跡性の規則

- ヒアリングシート5章・6章の各行（R-xx / E-xx）は、BR-### / EX-### のいずれか、または 前提（スコープ外とした理由付き）に**必ず**対応させる。取りこぼしがあってはならない。
- 各 BR-### / EX-### には `（出典: R-xx / 関連: FR-###）` の形式で出典と関連を書く。関連にはユーザーストーリー（`US1` など）を書いてもよい。
- ヒアリングシートに無い内容を補った場合（条件の追加、対象の絞り込み、今回の扱いの決定を含む）は、出典を `出典: R-xx、推定`（元の行が無ければ `出典: 推定`）とし、補った内容を 前提 にも記録する。
- ヒアリングシートの根拠が「慣習」のルールは、BR-### にしたうえで、正式なルールとして扱ってよいかを 前提 に「（R-xx、慣習のため要確認）」と記録する。
- 13章の未確定事項と同じ論点を含むルールや例外は、未確定の部分を BR-### / EX-### に含めず、前提 に「（Q-xx、要確認）」と記録する（`[NEEDS CLARIFICATION]` にしたものを除く）。
- To-Be 業務フローの各手順（TB-xx）は、少なくとも1つのユーザーストーリーの受け入れシナリオでカバーする。「システム」が行う手順は、その結果を利用者が確認できるシナリオとして書く。
- 13章の未確定事項は、アウトライン手順6の上限（`[NEEDS CLARIFICATION]` は最大3個）に従い、影響度の高いものだけをマーカーにする。残りは 前提 に「（Q-xx、要確認）」と付けて記録し、`/speckit-clarify` で扱えるようにする。

### B4. 業務要件セクションの扱い

- 業務システム（承認・申請・精算など、組織の規程に沿って人が操作する仕組み）の場合、`## 業務要件` を**必須セクション**として扱う。ヒアリングシートが無い場合も、機能説明から読み取れる範囲で記入する。
- 業務システムでない場合は、`## 業務要件` をセクションごと削除する。
- テンプレート中の `<!-- BEGIN speckit-ja:business-analysis -->` / `<!-- END speckit-ja:business-analysis -->` の行は、SPEC_FILE に残さない。
- 業務ルールと例外は、業務担当者が読んで正誤を判断できる言葉で書く。画面項目名、テーブル名、API には触れない。
- 数値や条件（金額、日数、回数、対象者）はヒアリングシートの値をそのまま書く。丸めたり言い換えたりしない。

### B5. 品質チェックリストへの追加項目

`## 業務要件` セクションがある場合に限り、アウトライン手順8a のチェックリストの `## 機能の準備状況` の後、`## 補足` の前に次のカテゴリを追加し、手順8b・8c の検証対象に含める。

```markdown
## 業務要件の網羅性

- [ ] ヒアリングシートの業務ルール（R-xx）が、すべて BR-### または 前提 に対応付けられている
- [ ] ヒアリングシートの例外（E-xx）が、すべて EX-### または 前提 に対応付けられている
- [ ] To-Be 業務フローの各手順（TB-xx）が、いずれかの受け入れシナリオでカバーされている
- [ ] 権限表のロールが、ユーザーストーリーのアクターと一致している
- [ ] 各 BR-### / EX-### に、検証できる FR-### またはシナリオが関連付けられている
- [ ] 業務ルールの数値・条件が具体的に書かれている（「適切に」「原則として」だけで終わっていない）
- [ ] 用語集の用語が仕様書全体で統一されている
```

ヒアリングシートを使っていない場合は、先頭2項目を「業務ルールと例外が、機能説明から読み取れる範囲で列挙されている」の1項目に置き換える。

### B6. 明確化の質問（手順8c）の言葉遣い

回答者は業務担当者（プログラミング経験のない人）であることを前提にする。

- 「ロール」「エンティティ」「ステータス」などの言葉は使わず、「誰が」「どの書類で」「どの段階で」と聞く。
- 回答候補は、業務の場面で起きることとして書く。例: 「A: 所属長が不在の間は、部長が代わりに承認する」
- 数値を聞く場合は、単位を明記する（円、日、件）。
- 質問の見出しには、対応するヒアリングシートの ID を付ける。例: `## 質問 1: 代理の承認者（Q-02）`

### B7. 完了報告への追加

完了報告に次を加える。

- 使用したヒアリングシートのパス（使っていない場合は「なし」）
- BR-### と EX-### の件数、そのうち「推定」を含む件数
- 手順8c で回答を得た未確定事項（Q-xx）の一覧。ヒアリングシート側の更新はユーザーに委ねる
- 前提 に回した未確定事項（Q-xx）と、慣習のため要確認としたルール（R-xx）の一覧

## 日本語出力ガードレール（Spec Kit 日本語版 / 全コマンド共通）

このセクションは Spec Kit 日本語版が全コマンドに付与する共通の後処理規約である。**省略してはならない。**

### G1. 成果物の記述言語

このコマンドがファイルを生成・更新する場合（`spec.md` / `plan.md` / `tasks.md` / `checklists/*.md` / `.specify/memory/constitution.md` / `research.md` / `data-model.md` / `quickstart.md` / `contracts/` 配下など）、その本文は**日本語**で記述すること。ユーザーへのチャット応答も日本語で行う。

次のものは例外として**英語のまま**維持する。

- ソースコード、シェルコマンド、識別子、型名、ファイルパス、ディレクトリ名、ブランチ名
- `[NEEDS CLARIFICATION: ...]`、`[P]`、`FR-###`、`SC-###`、`NFR-###`、`US1`/`US2`/`US3`、`T001` などの機械可読マーカーおよびID書式
- 業務分析拡張の ID 書式（`BR-###`、`EX-###`）と、ヒアリングシートの ID 書式（`AS-01`、`TB-01`、`R-01`、`E-01`、`Q-01`）
- `**Given**` / `**When**` / `**Then**`（Gherkin 記法）
- 外部ツールやこのコマンド自身が解釈する固定文字列（`EXECUTE_COMMAND:` など）
- 技術用語の原語表記が適切な場合の英単語（API、CI、OAuth など）

ユーザーが英語で指示した場合や、既存の成果物が英語で書かれている場合は、その言語に合わせてよい。それ以外は日本語を既定とする。

### G2. 文字化け検証（書き込み後に必ず実行）

ファイルの書き込み・編集が完了したら、**毎回**次の手順を実行する。

1. 書き込んだファイルを読み直す。
2. 次のいずれかに該当しないか確認する。
   - 置換文字 U+FFFD（いわゆる「黒ひし形に疑問符」の記号）が含まれる
   - mojibake パターンが含まれる（`ã`, `â`, `ï¿½`, `ãƒ`, `æ–‡`, `ð` で始まる不自然な連なりなど）
   - 日本語で書くべき本文が英語のままになっている（G1 の例外を除く）
   - 見出しや表が壊れている（列数の不一致、閉じていないコードフェンス）
3. 該当した場合は、そのファイルを **UTF-8 (BOMなし)** で**丸ごと書き直す**。差分パッチや部分置換で済ませない。
4. 書き直しを2回試しても解消しない場合は、作業を中断し、ユーザーに次を報告する。

   > 文字化けが解消しません。エディタまたは端末のエンコーディング設定（UTF-8 / コードページ）を確認してください。Windows PowerShell の場合は `$PSDefaultParameterValues['*:Encoding']='utf8'` と `chcp 65001` を確認してください。

### G3. 用語の統一

同一プロジェクト内では訳語を揺らさない。既に `spec.md` や `constitution.md` で使われている訳語があれば、それに合わせる。判断に迷う場合は英語を併記する（例: 受け入れシナリオ (acceptance scenario)）。
