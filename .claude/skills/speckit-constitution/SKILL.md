## ユーザー入力

```text
$ARGUMENTS
```

先に進む前に、ユーザー入力を（空でなければ）**必ず**考慮すること。

## スコープガード

本コマンド自身の作業は、プロジェクト憲法そのものの更新に限定される。依存するテンプレートや
コマンドは実行時に憲法を読み込むため、ここでは変更しない。

- ユーザー入力のすべての部分を、憲法の内容か、それとは別のガバナンス外の
  意図かに分類する。
- 入力に機能の実装、コード生成、リファクタリング、ビルド、デプロイの要求が
  含まれる場合、それらを実行することは**禁止**。代わりに保留意図として抽出する。
- アプリケーションのソースファイル、機能のルート、
  コンポーネント、テスト、デプロイ用ファイル、その他憲法ワークフローと
  無関係な成果物を作成・変更・削除することは**禁止**。
- ある指示が憲法の内容かどうか不明な場合は、変更を加える前に
  明確化を求める。
- 憲法の更新完了後、保留した各意図について `Next Actions` セクションを含める。
  元の意図を列挙し、適切な後続 Spec Kit コマンド、例えば
  `/speckit-specify` を、実行はせずに提案する。
- ガバナンス外の意図が存在しない場合は、`Next Actions` セクションを省略する。

## 実行前チェック

**拡張フックの確認（憲法更新の前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_constitution` キー配下のエントリを探す
- YAML がパースできない、または不正な場合、黙ってスキップしないこと。`.specify/extensions.yml` を読み取れなかったこと（パーサーのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めフックが一切確認されなかったことをユーザーに伝え、その上で通常どおり続行する
- `enabled` が明示的に `false` のフックを除外する。`enabled` フィールドを持たないフックは既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈または評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null／空の場合、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックをスキップし、条件の評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:
    ```
    ## 拡張フック

    **任意のプリフック**: {extension}
    コマンド: `/{command}`
    説明: {description}

    プロンプト: {prompt}
    実行するには: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## 拡張フック

    **自動プリフック**: {extension}
    実行中: `/{command}`
    EXECUTE_COMMAND: {command}

    アウトラインに進む前に、フックコマンドの結果を待つこと。
    ```
    上記のブロックを出力したら、続行する前に実際にフックを呼び出し、完了を待たなければならない。このエージェント／セッションで自分がそのコマンドを実行するのと同じ方法で実行すること（呼び出し方は上に示した文字どおりの `{command}` の ID とは異なる場合がある。例えば skills モードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
- フックが登録されていない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## アウトライン

`.specify/memory/constitution.md` にあるプロジェクト憲法を更新する。有効な憲法のスキャフォールドは、
コマンド実行時に Spec Kit のプリセット／テンプレート解決スタックを通じて `constitution-template` から
解決される。

以下の実行フローに従うこと:

1. リポジトリルートから `{SCRIPT}` を実行し、`TEMPLATE_CONTENT` を有効なテンプレートとしてパースする。
   - 共有リゾルバは、コアテンプレートへのフォールバックより前に、プロジェクトのオーバーライド、
     プリセットレイヤーの合成、拡張レイヤーを適用する。続行前に必ず成功しなければならない。
   - 失敗した場合は停止して解決エラーを報告する。寄与するテンプレートレイヤーが1つだけの状態で
     続行してはならない。
   - `.specify/memory/constitution.md` が存在する場合は、現在のプロジェクト固有の
     値と修正内容の取得元として読み込む。新たに解決したスキャフォールドを適用する際、
     引き続き該当する情報は保持する。
   - 存在しない場合は、解決されたテンプレートを初期ドキュメントとして使用する。
   - バージョン管理されたテンプレートレイヤーに書き戻さないこと。
   - `[ALL_CAPS_IDENTIFIER]` 形式のプレースホルダトークンをすべて特定する。
   **重要**: ユーザーはテンプレートで使われている数より少ない、または多い原則を必要とする場合がある。数が指定されていればそれに従うこと — 全体としてはテンプレートに従う。それに応じてドキュメントを更新すること。

2. プレースホルダの値を収集／導出する:
   - ユーザー入力（会話）が値を与えている場合は、それを使う。
   - そうでなければ既存のリポジトリのコンテキスト（README、ドキュメント、埋め込まれていれば過去の憲法バージョン）から推測する。
   - ガバナンス日付について: `RATIFICATION_DATE` は当初の採択日（不明なら問い合わせるか TODO を記す）、`LAST_AMENDED_DATE` は変更を加えた場合は本日、そうでなければ従来の値を保持する。
   - `CONSTITUTION_VERSION` はセマンティックバージョニングの規則に従ってインクリメントしなければならない:
     - MAJOR: 後方互換性のないガバナンス／原則の削除または再定義。
     - MINOR: 新しい原則／セクションの追加、またはガイダンスの実質的な拡充。
     - PATCH: 明確化、文言調整、誤字修正、意味を変えない改善。
   - バージョン上げの種別が曖昧な場合は、確定する前に根拠を提示する。

3. 解決されたテンプレートを必須の構造として用い、更新後の憲法の内容を起草する:
   - すべてのプレースホルダを具体的な文章に置き換える（角括弧のトークンを残してはならない。ただしプロジェクトがまだ定義しないと決めて意図的に残したテンプレートスロットは除き、残す場合は必ず明示的に正当化する）。
   - 見出しの階層を保持する。コメントは、置き換え後も明確化の助けになる場合を除き、削除してよい。
   - 各原則セクションが次を備えるようにする: 簡潔な名称行、譲れないルールを捉えた段落（または箇条書き）、自明でない場合は明示的な根拠。
   - ガバナンスのセクションが、改定手続き、バージョニング方針、コンプライアンスレビューの期待事項を列挙するようにする。

4. 更新後、憲法ファイルの先頭に HTML コメントとして Sync Impact Report を出力する。
   このレポートは改定を人間がレビューするための一時的な作業用素材であり、ガバナンスの内容ではない。
   改定後の憲法ファイルをコミットする前に削除されることが想定されている。
   - バージョン変更: 旧 → 新
   - 変更された原則の一覧（改名された場合は 旧タイトル → 新タイトル）
   - 追加されたセクション
   - 削除されたセクション
   - 意図的に保留したプレースホルダがあれば、その追跡 TODO。

5. 最終出力の前の検証:
   - 説明のない角括弧トークンが残っていないこと。
   - バージョン行がレポートと一致すること。
   - 日付が ISO 形式 YYYY-MM-DD であること。
   - 原則が宣言的かつ検証可能で、曖昧な表現がないこと（"should" → 適切な箇所で MUST/SHOULD とその根拠に置き換える）。

6. 完成した憲法を `.specify/memory/constitution.md` に書き戻す（上書き）。

7. 以下を含む最終サマリーをユーザーに出力する:
   - 新しいバージョンと、バージョンを上げた根拠。
   - 手動での追跡対応が必要な TODO プレースホルダや保留項目。
   - 推奨されるコミットメッセージ（例: `docs: amend constitution to vX.Y.Z (principle additions + governance update)`）。
   - 保留したガバナンス外の意図があれば、その `Next Actions` セクション。

書式とスタイルの要件:

- Markdown の見出しはテンプレートどおりに使う（レベルを下げたり上げたりしない）。
- 長い根拠の行は読みやすさを保つように折り返す（理想は100文字未満）が、不自然な改行で強制しない。
- セクション間は空行1行を保つ。
- 行末の空白を避ける。

ユーザーが部分的な更新（例: 1つの原則の改訂のみ）を与えた場合でも、検証とバージョン判定の手順は実施すること。

重要な情報が欠けている場合（例: 批准日が本当に不明）、`TODO(<FIELD_NAME>): explanation` を挿入し、Sync Impact Report の保留項目に含める。

`.specify/memory/constitution.md` のみを書くこと。テンプレートのソースファイルを作成・変更してはならない。

## 日本語出力ガードレール（Spec Kit 日本語版 / 全コマンド共通）

このセクションは Spec Kit 日本語版が全コマンドに付与する共通の後処理規約である。**省略してはならない。**

### G1. 成果物の記述言語

このコマンドがファイルを生成・更新する場合（`spec.md` / `plan.md` / `tasks.md` / `checklists/*.md` / `.specify/memory/constitution.md` / `research.md` / `data-model.md` / `quickstart.md` / `contracts/` 配下など）、その本文は**日本語**で記述すること。ユーザーへのチャット応答も日本語で行う。

次のものは例外として**英語のまま**維持する。

- ソースコード、シェルコマンド、識別子、型名、ファイルパス、ディレクトリ名、ブランチ名
- `[NEEDS CLARIFICATION: ...]`、`[P]`、`FR-###`、`SC-###`、`NFR-###`、`US1`/`US2`/`US3`、`T001` などの機械可読マーカーおよびID書式
- 業務分析拡張の ID 書式（`BR-###`、`EX-###`）と、ヒアリングシートの ID 書式（`AS-01`、`TB-01`、`R-01`、`E-01`、`Q-01`）
- `**Given**` / `**When**` / `**Then**`（Gherkin 記法）
- 外部ツールやこのコマンド自身が解釈する固定文字列（`EXECUTE_COMMAND:` など）
- 技術用語の原語表記が適切な場合の英単語（API、CI、OAuth など）

ユーザーが英語で指示した場合や、既存の成果物が英語で書かれている場合は、その言語に合わせてよい。それ以外は日本語を既定とする。

### G2. 文字化け検証（書き込み後に必ず実行）

ファイルの書き込み・編集が完了したら、**毎回**次の手順を実行する。

1. 書き込んだファイルを読み直す。
2. 次のいずれかに該当しないか確認する。
   - 置換文字 U+FFFD（いわゆる「黒ひし形に疑問符」の記号）が含まれる
   - mojibake パターンが含まれる（`ã`, `â`, `ï¿½`, `ãƒ`, `æ–‡`, `ð` で始まる不自然な連なりなど）
   - 日本語で書くべき本文が英語のままになっている（G1 の例外を除く）
   - 見出しや表が壊れている（列数の不一致、閉じていないコードフェンス）
3. 該当した場合は、そのファイルを **UTF-8 (BOMなし)** で**丸ごと書き直す**。差分パッチや部分置換で済ませない。
4. 書き直しを2回試しても解消しない場合は、作業を中断し、ユーザーに次を報告する。

   > 文字化けが解消しません。エディタまたは端末のエンコーディング設定（UTF-8 / コードページ）を確認してください。Windows PowerShell の場合は `$PSDefaultParameterValues['*:Encoding']='utf8'` と `chcp 65001` を確認してください。

### G3. 用語の統一

同一プロジェクト内では訳語を揺らさない。既に `spec.md` や `constitution.md` で使われている訳語があれば、それに合わせる。判断に迷う場合は英語を併記する（例: 受け入れシナリオ (acceptance scenario)）。
