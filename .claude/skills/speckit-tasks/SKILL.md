## ユーザー入力

```text
$ARGUMENTS
```

先に進む前に、（空でなければ）ユーザー入力を**必ず**考慮すること。

## 実行前チェック

**拡張フックの確認（タスク生成の前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合はそれを読み、`hooks.before_tasks` キー配下のエントリを探す
- YAML がパースできない、または不正な場合は黙ってスキップしない: `.specify/extensions.yml` を読めなかったこと（パーサーのエラーを含める）、およびそこに登録された必須（`optional: false`）フックを含めてフックが一切チェックされなかったことをユーザーに伝え、その後は通常どおり続行する
- `enabled` が明示的に `false` のフックを除外する。`enabled` フィールドを持たないフックは既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null/空の場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```
    上記のブロックを出力した後、続行する前に実際にフックを起動し、その完了を待つこと。自分がこのエージェント／セッションでそのコマンドを実行するのと同じやり方で実行する（起動方法は上に示した文字どおりの `{command}` ID とは異なる場合がある。例: skills モードのエージェントは `/skill:speckit-...` または `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
- フックが1つも登録されていない場合、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## 概略

1. **セットアップ**: リポジトリルートから `{SCRIPT}` を実行し、FEATURE_DIR、TASKS_TEMPLATE_CONTENT、TASKS_TEMPLATE、および AVAILABLE_DOCS のリストをパースする。`FEATURE_DIR` と `TASKS_TEMPLATE` は、提供される場合は絶対パスでなければならない。`AVAILABLE_DOCS` は `FEATURE_DIR` 配下で利用可能なドキュメント名／相対パスのリストである（例: `research.md` や `contracts/`）。"I'm Groot" のように引数にシングルクォートが含まれる場合は、エスケープ記法を使う: 例 'I'\''m Groot'（可能ならダブルクォートでもよい: "I'm Groot"）。

2. **設計ドキュメントの読み込み**: FEATURE_DIR から読み込む:
   - **必須**: plan.md（技術スタック、ライブラリ、構成）、spec.md（優先度付きのユーザーストーリー）
   - **任意**: data-model.md（エンティティ）、contracts/（インターフェース契約）、research.md（決定事項）、quickstart.md（テストシナリオ）
   - **存在する場合**: プロジェクトの原則とガバナンス上の制約のため `/memory/constitution.md` を読み込む
   - 注意: すべてのプロジェクトがすべてのドキュメントを持つわけではない。利用可能なものに基づいてタスクを生成すること。

3. **タスク生成ワークフローの実行**:
   - plan.md を読み込み、技術スタック、ライブラリ、プロジェクト構成を抽出する
   - spec.md を読み込み、優先度（P1、P2、P3 など）付きのユーザーストーリーを抽出する
   - data-model.md が存在する場合: エンティティを抽出し、ユーザーストーリーに対応付ける
   - contracts/ が存在する場合: インターフェース契約をユーザーストーリーに対応付ける
   - research.md が存在する場合: セットアップタスク向けの決定事項を抽出する
   - ユーザーストーリー単位で整理したタスクを生成する（後述の「タスク生成ルール」を参照）
   - ユーザーストーリーの完了順序を示す依存関係グラフを生成する
   - ユーザーストーリーごとに並列実行例を作成する
   - タスクの網羅性を検証する（各ユーザーストーリーが必要なタスクをすべて持ち、独立してテスト可能であること）

4. **tasks.md の生成**: 上記の JSON 出力から得た TASKS_TEMPLATE_CONTENT を構造として使う。TASKS_TEMPLATE_CONTENT を出力しない旧いセットアップスクリプトとの互換のため、その場合は代わりに TASKS_TEMPLATE を読む。以下を埋める:
   - plan.md から得た正しい機能名
   - フェーズ1: セットアップタスク（プロジェクトの初期化）
   - フェーズ2: 基盤構築タスク（すべてのユーザーストーリーに対するブロッキング前提）
   - フェーズ3以降: ユーザーストーリーごとに1フェーズ（spec.md の優先度順）
   - 各フェーズに含めるもの: ストーリーのゴール、独立テスト基準、テスト（要求された場合）、実装タスク
   - 最終フェーズ: 仕上げと横断的関心事
   - すべてのタスクは厳密なチェックリスト形式に従わなければならない（後述の「タスク生成ルール」を参照）
   - 各タスクに明確なファイルパス
   - ストーリーの完了順序を示す依存関係セクション
   - ストーリーごとの並列実行例
   - 実装戦略セクション（MVPファースト、漸進的デリバリー）

## タスク生成ルール

**重要**: 独立した実装とテストを可能にするため、タスクはユーザーストーリー単位で整理**しなければならない**。

**テストは任意**: テストタスクは、機能仕様書で明示的に要求された場合、またはユーザーが TDD アプローチを要求した場合にのみ生成する。

### チェックリスト形式（必須）

すべてのタスクは、この形式に厳密に従わなければならない:

```text
- [ ] [TaskID] [P?] [Story?] Description with file path
```

**形式の構成要素**:

1. **チェックボックス**: 必ず `- [ ]`（Markdown のチェックボックス）で始める
2. **タスクID**: 実行順に連番（T001、T002、T003…）
3. **[P] マーカー**: タスクが並列化可能な場合にのみ付ける（別ファイルであり、未完了タスクへの依存がないこと）
4. **[Story] ラベル**: ユーザーストーリーフェーズのタスクにのみ必須
   - 形式: [US1]、[US2]、[US3] など（spec.md のユーザーストーリーに対応）
   - セットアップフェーズ: ストーリーラベルなし
   - 基盤構築フェーズ: ストーリーラベルなし
   - ユーザーストーリーフェーズ: ストーリーラベル必須
   - 仕上げフェーズ: ストーリーラベルなし
5. **説明**: 正確なファイルパスを伴う明確なアクション

**例**:

- ✅ 正: `- [ ] T001 Create project structure per implementation plan`
- ✅ 正: `- [ ] T005 [P] Implement authentication middleware in src/middleware/auth.py`
- ✅ 正: `- [ ] T012 [P] [US1] Create User model in src/models/user.py`
- ✅ 正: `- [ ] T014 [US1] Implement UserService in src/services/user_service.py`
- ❌ 誤: `- [ ] Create User model`（ID とストーリーラベルが欠落）
- ❌ 誤: `T001 [US1] Create model`（チェックボックスが欠落）
- ❌ 誤: `- [ ] [US1] Create User model`（タスクIDが欠落）
- ❌ 誤: `- [ ] T001 [US1] Create model`（ファイルパスが欠落）

### タスクの整理

1. **ユーザーストーリーから（spec.md）** - 主たる整理軸:
   - 各ユーザーストーリー（P1、P2、P3…）は専用のフェーズを持つ
   - 関連するコンポーネントをすべてそのストーリーに対応付ける:
     - そのストーリーに必要なモデル
     - そのストーリーに必要なサービス
     - そのストーリーに必要なインターフェース／UI
     - テストが要求された場合: そのストーリー固有のテスト
   - ストーリー間の依存を明示する（ほとんどのストーリーは独立しているべき）

2. **契約から**:
   - 各インターフェース契約 → それが担うユーザーストーリーへ対応付ける
   - テストが要求された場合: 各インターフェース契約 → そのストーリーのフェーズ内で、実装より前に契約テストタスク [P] を置く

3. **データモデルから**:
   - 各エンティティを、それを必要とするユーザーストーリーに対応付ける
   - エンティティが複数のストーリーにまたがる場合: 最も早いストーリー、またはセットアップフェーズに置く
   - 関連 → 適切なストーリーフェーズ内のサービス層タスクへ
   - data-model.md で制約を持つ各フィールド（最大長、nullable／必須、列挙値、バリデーション規則）については、実装時の裁量に委ねられないよう、その制約をタスクの説明に逐語で引用する

4. **セットアップ／インフラから**:
   - 共通基盤 → セットアップフェーズ（フェーズ1）
   - 基盤的・ブロッキングなタスク → 基盤構築フェーズ（フェーズ2）
   - ストーリー固有のセットアップ → そのストーリーのフェーズ内

### フェーズ構成

- **フェーズ1**: セットアップ（プロジェクトの初期化）
- **フェーズ2**: 基盤構築（ブロッキング前提 — ユーザーストーリーの前に完了させなければならない）
- **フェーズ3以降**: 優先度順のユーザーストーリー（P1、P2、P3…）
  - 各ストーリー内: テスト（要求された場合）→ モデル → サービス → エンドポイント → 結合
  - 各フェーズは、完結し独立してテスト可能なインクリメントであること
- **最終フェーズ**: 仕上げと横断的関心事

## 完了条件

- [ ] すべてのフェーズ、タスクID、ファイルパスを備えた tasks.md が生成されている
- [ ] 上記「必須の実行後フック」のルールに従って拡張フックがディスパッチまたはスキップされている
- [ ] タスク数、ストーリー別内訳、MVP スコープとともに完了がユーザーに報告されている

## 業務分析拡張（Spec Kit 日本語版）

このセクションは、業務システムの要件分析を補強するために Spec Kit 日本語版が追加した規約である。spec.md に `## 業務要件` セクションがある場合に適用する。無い場合は本セクションを無視する。

- 業務ルール（BR-###）と業務上の例外処理（EX-###）を、FR-### と同じく要件として扱い、実装するタスクを生成する。
- BR-### / EX-### を実装またはテストするタスクの説明には、その ID を含める。例: `- [ ] T021 [US1] 宿泊費が上限を超える明細に理由の入力を必須にする（BR-003） in src/lib/rules/lodging.ts`
- 権限表で「×」（できない）または「△」（条件付き）の操作は、認可を実装するタスクを含める。テストを生成する場合は、許可されないことを確認するテストタスクも含める。
- 用語集の用語を、タスクの説明にもそのまま使う。

## 日本語出力ガードレール（Spec Kit 日本語版 / 全コマンド共通）

このセクションは Spec Kit 日本語版が全コマンドに付与する共通の後処理規約である。**省略してはならない。**

### G1. 成果物の記述言語

このコマンドがファイルを生成・更新する場合（`spec.md` / `plan.md` / `tasks.md` / `checklists/*.md` / `.specify/memory/constitution.md` / `research.md` / `data-model.md` / `quickstart.md` / `contracts/` 配下など）、その本文は**日本語**で記述すること。ユーザーへのチャット応答も日本語で行う。

次のものは例外として**英語のまま**維持する。

- ソースコード、シェルコマンド、識別子、型名、ファイルパス、ディレクトリ名、ブランチ名
- `[NEEDS CLARIFICATION: ...]`、`[P]`、`FR-###`、`SC-###`、`NFR-###`、`US1`/`US2`/`US3`、`T001` などの機械可読マーカーおよびID書式
- 業務分析拡張の ID 書式（`BR-###`、`EX-###`）と、ヒアリングシートの ID 書式（`AS-01`、`TB-01`、`R-01`、`E-01`、`Q-01`）
- `**Given**` / `**When**` / `**Then**`（Gherkin 記法）
- 外部ツールやこのコマンド自身が解釈する固定文字列（`EXECUTE_COMMAND:` など）
- 技術用語の原語表記が適切な場合の英単語（API、CI、OAuth など）

ユーザーが英語で指示した場合や、既存の成果物が英語で書かれている場合は、その言語に合わせてよい。それ以外は日本語を既定とする。

### G2. 文字化け検証（書き込み後に必ず実行）

ファイルの書き込み・編集が完了したら、**毎回**次の手順を実行する。

1. 書き込んだファイルを読み直す。
2. 次のいずれかに該当しないか確認する。
   - 置換文字 U+FFFD（いわゆる「黒ひし形に疑問符」の記号）が含まれる
   - mojibake パターンが含まれる（`ã`, `â`, `ï¿½`, `ãƒ`, `æ–‡`, `ð` で始まる不自然な連なりなど）
   - 日本語で書くべき本文が英語のままになっている（G1 の例外を除く）
   - 見出しや表が壊れている（列数の不一致、閉じていないコードフェンス）
3. 該当した場合は、そのファイルを **UTF-8 (BOMなし)** で**丸ごと書き直す**。差分パッチや部分置換で済ませない。
4. 書き直しを2回試しても解消しない場合は、作業を中断し、ユーザーに次を報告する。

   > 文字化けが解消しません。エディタまたは端末のエンコーディング設定（UTF-8 / コードページ）を確認してください。Windows PowerShell の場合は `$PSDefaultParameterValues['*:Encoding']='utf8'` と `chcp 65001` を確認してください。

### G3. 用語の統一

同一プロジェクト内では訳語を揺らさない。既に `spec.md` や `constitution.md` で使われている訳語があれば、それに合わせる。判断に迷う場合は英語を併記する（例: 受け入れシナリオ (acceptance scenario)）。
