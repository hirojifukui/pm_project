## ユーザー入力

```text
$ARGUMENTS
```

続行する前に、ユーザー入力を**必ず**考慮すること（空でない場合）。

## 実行前チェック

**拡張フックの確認（収束処理の前）**:

- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_converge` キー配下のエントリを探す
- YAML がパースできない、または不正な場合は黙ってスキップしない: `.specify/extensions.yml` を読み込めなかったこと（パーサーのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めて一切のフックが確認されなかったことをユーザーに伝え、その後は通常どおり続行する
- `enabled` が明示的に `false` のフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈または評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null/空の場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:

    ```text
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

  - **必須フック**（`optional: false`）:

    ```text
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Goal.
    ```
    上記のブロックを出力したあと、実際にフックを呼び出し、その完了を待ってから続行することが**必須**である。このエージェント/セッションで自分がそのコマンドを実行するのと同じ方法で実行すること（実際の呼び出し方は上に示した `{command}` の ID そのものとは異なる場合がある。例えば skills モードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。

- フックが1つも登録されていない場合、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## 目的

機能の仕様書・計画・タスクが求めているものと、コードベースが現時点で実装しているものとの
差分を埋める。`spec.md`、`plan.md`、`tasks.md` を**唯一の意図の出典**として読み
（憲法は統制上の制約として扱う）、コードの現状を
評価し、どの要件・受け入れ基準・計画上の決定・
既存タスクが未達成・未完了・部分的にしか満たされていないかを判定し、**残作業の各項目を
新しい追跡可能なタスクとして** `tasks.md` の末尾に**追記**して、
`/speckit-implement` がそれを完了できるようにする。このコマンドは、現在の `tasks.md` に対して
`/speckit-implement` が実行済みであり、かつ `/speckit-tasks` が完全な `tasks.md` を生成済みである場合にのみ実行することが必須である。

これは差分ツール**ではなく**、変更履歴を追跡**しない**。機能の成果物を基準として
コードの現在の状態を評価する — git も、ブランチ比較も、履歴も使わない。

## 動作上の制約

**追記のみ、決して書き換えない**: このコマンドが行う書き込みは、`tasks.md` に新しい
`## フェーズN: 収束` セクションを追記することの**み**である。以下は禁止である:

- `spec.md` や `plan.md` をいかなる形でも変更すること;
- 既存のタスク（過去の収束フェーズのタスクを含む）を書き換え、採番し直し、並べ替え、
  削除すること;
- アプリケーションコードを変更・作成・削除すること — 追記したタスクを完了させるのは
  `/speckit-implement` の仕事である。

コードベースがすでにすべてを満たしている場合、このコマンドは `tasks.md` を
**1バイトも変更しない**まま残し（空の収束ヘッダーも作らない）、クリーンな結果を報告することが必須である。

**憲法の権威**: プロジェクトの憲法（`/memory/constitution.md`）は
**交渉の余地がない**。MUST 原則に違反するコードは最も重大度の高い検出事項であり、
対応する是正タスクを生成する。憲法が未記入のテンプレートである場合は、
失敗させるのではなく憲法チェックを穏当にスキップする。

## 実行手順

### 1. 収束コンテキストの初期化

リポジトリルートから `{SCRIPT}` を一度実行し、JSON をパースして FEATURE_DIR と AVAILABLE_DOCS を得る。絶対パスを導出する:

- SPEC = FEATURE_DIR/spec.md
- PLAN = FEATURE_DIR/plan.md
- TASKS = FEATURE_DIR/tasks.md
- CONSTITUTION = `/memory/constitution.md`（存在する場合）
`spec.md`、`plan.md`、`tasks.md` のいずれかが欠けている場合は、実行すべき前提コマンドを名指しした
明確で実行可能なメッセージとともに中止する（仕様書がなければ `/speckit-specify`、計画がなければ `/speckit-plan`、
タスクがなければ `/speckit-tasks`）。部分的な出力を生成しないこと。
"I'm Groot" のように引数にシングルクォートが含まれる場合は、エスケープ構文を使う: 例 'I'\''m Groot'（可能ならダブルクォートでもよい: "I'm Groot"）。

### 2. 成果物の読み込み（漸進的開示）

各成果物から、必要最小限のコンテキストのみを読み込む:

**spec.md から:**

- 機能要件（FR-###）
- 成功基準（SC-###） — 構築作業を伴う項目のみを含める。ローンチ後の成果指標や
  ビジネス KPI は除外する
- ユーザーストーリーとその受け入れシナリオ
- エッジケース（存在する場合）

**plan.md から:**

- アーキテクチャ/スタックの選択と技術的決定
- データモデルへの参照
- フェーズと名前の挙がっている接点（計画が作成または編集すると述べているファイル/コンポーネント）
- 技術的制約

**tasks.md から:**

- タスクID（次のIDと次のフェーズ番号を算出するため）
- 説明、フェーズのグルーピング、参照されているファイルパス

**憲法から（未記入のテンプレートでない場合）:**

- 原則名と MUST/SHOULD の規範的記述

### 3. 意図インベントリの構築

内部モデルを作成する（生の成果物をそのまま出力しないこと）:

- **要件インベントリ**: FR-### / SC-### / ユーザーストーリーの受け入れシナリオごとに
  1つの安定したキーを割り当て（例 `US1/AC2`）、さらに構築上の義務を課す計画上の決定と
  憲法原則を加える。
- **コードスコープマップ**: `plan.md` と `tasks.md` で名前の挙がっているファイルパスに加え、
  各要件が述べている概念のキーワード検索から、評価対象となるソースファイルと
  コンポーネントの集合を導出する。評価はこれらに限定すること — 成果物が定義している範囲を
  超えてスコープを推測**しない**こと。

### 4. コードベースの評価と検出事項の分類

意図インベントリの各項目について、スコープ内の現在のコードを調査し、
ギャップがある箇所にのみ `Finding` を生成する。すべての検出事項を**ギャップ種別**で分類する:

- **`missing`**: 必要な作業がコードにまったく存在しない。
- **`partial`**: 作業は存在するが、要件 / 受け入れ基準 / 計画上の決定を
  まだ完全には満たしていない。
- **`contradicts`**: コードが、表明された意図または憲法の MUST 原則と
  衝突する動作をしている。
- **`unrequested`**: 仕様書・計画・タスクが求めていない作業がコードに含まれている
  （認識のために可視化する — converge はコードを削除**しない**。レビュー/正当化または
  削除を行うタスクを追記するだけである）。

各 `Finding` は次を記録する: 安定したid、追跡先の `source-ref`、`gap-type`、
重大度、そして根拠（観察したファイル/領域）を含む短い人間可読な説明。

**エッジケース:**

- **コードがほとんど、またはまったくない場合**: 失敗させるのではなく、仕様化されたスコープ全体を
  `missing` の残作業として扱う。
- **残作業がない場合**: 検出事項をゼロ件とし、手順7の収束済みの分岐に従う。

### 5. 重大度の割り当て

- **CRITICAL**: 憲法の MUST 原則に違反している、または P1 ユーザーストーリーの基本機能を
  阻害する `missing`/`contradicts` のギャップ。
- **HIGH**: 中核的な機能要件または受け入れ基準における `missing` または `partial` の
  ギャップ。
- **MEDIUM**: 副次的な要件における `partial` のギャップ、または正当性が不明確な
  `unrequested` の追加。
- **LOW**: 軽微な部分的ギャップ、仕上げ、または低リスクな `unrequested` の追加。

### 6. セッション内での検出事項サマリーの提示

何かを追記する前に、重大度で段階分けしたコンパクトなサマリーを出力する（この時点ではファイル書き込みを行わない）:

## 収束の検出事項

| ID | ギャップ種別 | 重大度 | 出典 | 根拠 | 残作業 |
|----|----------|----------|--------|----------|----------------|
| F1 | missing  | HIGH     | FR-008 | 例: tasks.md への書き込み時に path/to/module.py で追記専用ガードが検出されない | 追記専用の強制を追加 |

**サマリー指標:**

- 確認した要件 / 受け入れ基準
- 確認した計画上の決定
- 確認した憲法原則（または「スキップ — テンプレート」）
- ギャップ種別ごとの検出事項件数（missing / partial / contradicts / unrequested）
- 重大度ごとの検出事項件数

### 7. 収束タスクの追記（または収束済みの報告）

**対応可能な検出事項が1件以上ある場合**（`tasks_appended` の結果）:

追記の取り決めに従い、`tasks.md` の**末尾**に追記する:

1. 既存のタスクIDをすべて走査し、その最大値を `M` とする。次のフェーズ番号 `N`
   （既存の最大フェーズ + 1）を決定する。
2. 新しいセクションヘッダー `## フェーズN: 収束` を1つだけ書く。
3. 対応可能な検出事項ごとにチェックリスト項目を1つ出力する。CRITICAL/HIGH を先頭に並べ、
   ゼロ埋めしたID `T{M+1:03d}, T{M+2:03d}, …` を割り当てる:

   ```markdown
   - [ ] T042 <imperative description> per <source-ref> (<gap-type>)
   ```

   `<source-ref>` はタスクをその出自に紐づける: 例 `FR-003`、`SC-002`、
   `US1/AC2`、`plan: storage decision`、`Constitution II`。

   `<gap-type>` は `missing`、`partial`、`contradicts`、`unrequested` のいずれかである。

   憲法違反のタスクは最初に出力し、`CRITICAL` として
   記述することが必須である。
4. 既存のIDを再利用したり採番し直したりしないこと。過去の収束フェーズが存在する場合は、その下に
   別番号の新しいものを追加する — 古いものには手を触れない。

**対応可能な検出事項がない場合**（`converged` の結果）:

- `tasks.md` を一切変更**しない** — 空のフェーズヘッダーも作らない。
- 次のように報告する: **「✅ 収束済み — 実装は仕様書・計画・タスクを満たしている。」**
- 何を確認したかのサマリー件数を含める。

### 8. 次のアクションの提示（引き継ぎ）

- `tasks_appended` の場合: どのフェーズの下にいくつのタスクを追記したかを述べ、
  それらを完了させるために `/speckit-implement` の実行を推奨する。加えて、再度 converge を
  実行すれば残項目がより少なくなるか、なくなることを補足する。
- `converged` の場合: レビューへの移行 / PR の作成を推奨する。この機能の仕様化されたスコープに対して、
  これ以上の implement パスは不要である。

### 9. 拡張フックの確認

結果を生成したあと、プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。

- 存在する場合は読み込み、`hooks.after_converge` キー配下のエントリを探す
- YAML がパースできない、または不正な場合は黙ってスキップしない: `.specify/extensions.yml` を読み込めなかったこと（パーサーのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めて一切のフックが確認されなかったことをユーザーに伝え、その後は通常どおり続行する
- `enabled` が明示的に `false` のフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈または評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null/空の場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- 任意の後続コマンドを実行するかどうかをユーザーが判断できるよう、フックを列挙する前に
  収束の結果（`converged` または `tasks_appended`）をセッション内で報告する。
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:

    ```text
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

  - **必須フック**（`optional: false`）:

    ```text
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    上記のブロックを出力したあと、実際にフックを呼び出し、その完了を待ってから続行することが**必須**である。このエージェント/セッションで自分がそのコマンドを実行するのと同じ方法で実行すること（実際の呼び出し方は上に示した `{command}` の ID そのものとは異なる場合がある。例えば skills モードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。

- フックが1つも登録されていない場合、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## 日本語出力ガードレール（Spec Kit 日本語版 / 全コマンド共通）

このセクションは Spec Kit 日本語版が全コマンドに付与する共通の後処理規約である。**省略してはならない。**

### G1. 成果物の記述言語

このコマンドがファイルを生成・更新する場合（`spec.md` / `plan.md` / `tasks.md` / `checklists/*.md` / `.specify/memory/constitution.md` / `research.md` / `data-model.md` / `quickstart.md` / `contracts/` 配下など）、その本文は**日本語**で記述すること。ユーザーへのチャット応答も日本語で行う。

次のものは例外として**英語のまま**維持する。

- ソースコード、シェルコマンド、識別子、型名、ファイルパス、ディレクトリ名、ブランチ名
- `[NEEDS CLARIFICATION: ...]`、`[P]`、`FR-###`、`SC-###`、`NFR-###`、`US1`/`US2`/`US3`、`T001` などの機械可読マーカーおよびID書式
- 業務分析拡張の ID 書式（`BR-###`、`EX-###`）と、ヒアリングシートの ID 書式（`AS-01`、`TB-01`、`R-01`、`E-01`、`Q-01`）
- `**Given**` / `**When**` / `**Then**`（Gherkin 記法）
- 外部ツールやこのコマンド自身が解釈する固定文字列（`EXECUTE_COMMAND:` など）
- 技術用語の原語表記が適切な場合の英単語（API、CI、OAuth など）

ユーザーが英語で指示した場合や、既存の成果物が英語で書かれている場合は、その言語に合わせてよい。それ以外は日本語を既定とする。

### G2. 文字化け検証（書き込み後に必ず実行）

ファイルの書き込み・編集が完了したら、**毎回**次の手順を実行する。

1. 書き込んだファイルを読み直す。
2. 次のいずれかに該当しないか確認する。
   - 置換文字 U+FFFD（いわゆる「黒ひし形に疑問符」の記号）が含まれる
   - mojibake パターンが含まれる（`ã`, `â`, `ï¿½`, `ãƒ`, `æ–‡`, `ð` で始まる不自然な連なりなど）
   - 日本語で書くべき本文が英語のままになっている（G1 の例外を除く）
   - 見出しや表が壊れている（列数の不一致、閉じていないコードフェンス）
3. 該当した場合は、そのファイルを **UTF-8 (BOMなし)** で**丸ごと書き直す**。差分パッチや部分置換で済ませない。
4. 書き直しを2回試しても解消しない場合は、作業を中断し、ユーザーに次を報告する。

   > 文字化けが解消しません。エディタまたは端末のエンコーディング設定（UTF-8 / コードページ）を確認してください。Windows PowerShell の場合は `$PSDefaultParameterValues['*:Encoding']='utf8'` と `chcp 65001` を確認してください。

### G3. 用語の統一

同一プロジェクト内では訳語を揺らさない。既に `spec.md` や `constitution.md` で使われている訳語があれば、それに合わせる。判断に迷う場合は英語を併記する（例: 受け入れシナリオ (acceptance scenario)）。
