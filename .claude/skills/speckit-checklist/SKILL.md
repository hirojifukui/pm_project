## チェックリストの目的: 「英語のためのユニットテスト」

**重要な概念**: チェックリストは**要件記述のためのユニットテスト**である — 対象ドメインにおける要件の品質・明確さ・完全性を検証するものである。

**検証/テストのためのものではない**:

- ❌ 「ボタンが正しくクリックされることを検証する」ではない
- ❌ 「エラー処理が動作することをテストする」ではない
- ❌ 「API が 200 を返すことを確認する」ではない
- ❌ コード/実装が仕様書と一致しているかの確認ではない

**要件品質の検証のためのもの**:

- ✅ 「すべてのカード種別に対して視覚的階層の要件が定義されているか?」（完全性）
- ✅ 「『目立つ表示』は具体的なサイズ/配置で定量化されているか?」（明確さ）
- ✅ 「ホバー状態の要件はすべてのインタラクティブ要素で一貫しているか?」（一貫性）
- ✅ 「キーボードナビゲーションに関するアクセシビリティ要件は定義されているか?」（網羅性）
- ✅ 「ロゴ画像の読み込みに失敗したときに何が起きるかを仕様書は定義しているか?」（エッジケース）

**比喩**: 仕様書が英語で書かれたコードだとすれば、チェックリストはそのユニットテストスイートである。ここでテストするのは、要件が適切に書かれているか、完全か、曖昧でないか、実装に着手できる状態かであって、実装が動作するかどうかではない。

**所有権とチェックボックスのライフサイクル**:

- このコマンドが生成するカスタムチェックリストは、レビュアーが所有する要件品質レビューの成果物である。
- `[x]` は、レビュアーがその要件品質基準を満たしていると判断したことを意味する。
- `[x]` は実装作業が完了したことを意味**しない**。
- このコマンドはチェック項目を生成または追記するものであり、生成した項目を `[x]` にすることは**禁止**。
- エージェントが項目の評価を支援してよいのは、レビュアーから明示的に依頼された場合のみである。
- `checklists/requirements.md` は `/speckit-specify` と `/speckit-clarify` が保守する、別個の組み込み仕様品質チェックリストである。この例外を、ここで生成するカスタムチェックリストに適用してはならない。

## ユーザー入力

```text
$ARGUMENTS
```

先に進む前に、ユーザー入力（空でない場合）を**必ず**考慮すること。

## 実行前チェック

**拡張フックの確認（チェックリスト生成前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_checklist` キー配下のエントリを探す
- YAML がパースできない、または不正な場合は黙ってスキップしないこと。`.specify/extensions.yml` を読めなかったこと（パーサーのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めてフックが一切チェックされなかったことをユーザーに伝え、その後は通常どおり続行する
- `enabled` が明示的に `false` のフックは除外する。`enabled` フィールドを持たないフックは既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null/空の場合は、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Execution Steps.
    ```
    上記ブロックを出力した後、続行する前に実際にフックを**必ず**呼び出し、完了を待つこと。このエージェント/セッションで自分がそのコマンドを実行するのと同じ方法で実行する（呼び出し方は上に示した文字どおりの `{command}` ID とは異なる場合がある。例えば skills モードのエージェントは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
- フックが1つも登録されていない場合、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## 実行ステップ

1. **セットアップ**: リポジトリルートから `{SCRIPT}` を実行し、JSON をパースして FEATURE_DIR、AVAILABLE_DOCS リスト、TEMPLATE_CONTENT を取得する。
   - すべてのファイルパスは絶対パスであること。
   - "I'm Groot" のように引数内にシングルクォートが含まれる場合は、エスケープ記法を使う: 例 'I'\''m Groot'（可能ならダブルクォートでもよい: "I'm Groot"）。

2. **存在する場合**: プロジェクトの原則とガバナンス制約のため `/memory/constitution.md` を読み込む。

3. **意図の明確化（動的）**: 最大3つの初期コンテキスト明確化質問を導出する（あらかじめ用意されたカタログは使わない）。質問は以下を**必ず**満たすこと:
   - ユーザーの言い回しと、仕様書/計画/タスクから抽出したシグナルから生成すること
   - チェックリストの内容を実質的に変える情報のみを尋ねること
   - `$ARGUMENTS` で既に明確な項目は個別にスキップすること
   - 網羅性より精度を優先すること

   生成アルゴリズム:
   1. シグナルを抽出する: 機能ドメインのキーワード（例: 認証、レイテンシ、UX、API）、リスク指標（"critical"、"must"、"compliance"）、ステークホルダーの示唆（"QA"、"レビュー"、"セキュリティチーム"）、明示的な成果物（"a11y"、"ロールバック"、"契約"）。
   2. シグナルを候補となる重点領域（最大4つ）にクラスタリングし、関連度でランク付けする。
   3. 明示されていなければ、想定される対象者と利用タイミング（作成者、レビュアー、QA、リリース）を特定する。
   4. 欠けている観点を検出する: スコープの広さ、深さ/厳格さ、リスクの重点、除外境界、測定可能な受け入れ基準。
   5. 次の原型から質問を選んで組み立てる:
      - スコープの精緻化（例: 「X と Y との統合接点も含めるべきか、それともローカルモジュールの正しさに限定するか?」）
      - リスクの優先順位付け（例: 「これらの潜在的リスク領域のうち、必須のゲートチェックを設けるべきものはどれか?」）
      - 深さの調整（例: 「これはコミット前の軽量な健全性チェックリストか、それとも正式なリリースゲートか?」）
      - 対象者の枠組み（例: 「作成者のみが使うのか、PR レビュー時に同僚も使うのか?」）
      - 境界の除外（例: 「今回はパフォーマンスチューニングの項目を明示的に除外すべきか?」）
      - シナリオクラスの欠落（例: 「復旧フローが検出されない — ロールバック／部分障害の経路はスコープ内か?」）

   質問の書式ルール:
   - 選択肢を提示する場合は、Option | Candidate | Why It Matters の列を持つコンパクトな表を生成する
   - 選択肢は最大 A〜E まで。自由記述のほうが明確なら表は省く
   - ユーザーが既に述べたことを言い直させてはならない
   - 推測に基づくカテゴリを避ける（ハルシネーション禁止）。不確かな場合は明示的に尋ねる: 「X がスコープに含まれるか確認してほしい。」

   対話が不可能な場合の既定値:
   - 深さ: 標準
   - 対象者: コード関連ならレビュアー（PR）、それ以外は作成者
   - 重点: 関連度上位2クラスタ

   質問を出力する（Q1/Q2/Q3 とラベル付けする）。回答後、シナリオクラス（代替 / 例外 / 復旧 / 非機能ドメイン）が2つ以上不明なままであれば、それぞれ1行の根拠（例: 「復旧経路のリスクが未解決」）を付けて、対象を絞った追加質問を最大2つ（Q4/Q5）**任意**で行ってよい。合計5問を超えてはならない。ユーザーが追加質問を明示的に断った場合はエスカレーションをスキップする。

4. **ユーザー要求の理解**: `$ARGUMENTS` と明確化の回答を統合する:
   - チェックリストのテーマを導出する（例: セキュリティ、レビュー、デプロイ、UX）
   - ユーザーが明示した必須項目をまとめる
   - 選択された重点をカテゴリの骨組みに対応付ける
   - 不足しているコンテキストは仕様書/計画/タスクから推測する（ハルシネーション**禁止**）

5. **機能コンテキストの読み込み**: FEATURE_DIR から読み込む:
   - spec.md: 機能の要件とスコープ
   - plan.md（存在する場合）: 技術的詳細、依存関係
   - tasks.md（存在する場合）: 実装タスク

   **コンテキスト読み込み戦略**:
   - 有効な重点領域に関連する必要部分のみを読み込む（ファイル全体の丸投げを避ける）
   - 長いセクションは簡潔なシナリオ/要件の箇条書きに要約することを優先する
   - 段階的開示を用いる: ギャップを検出した場合にのみ追加取得を行う
   - 元ドキュメントが大きい場合は、生テキストを埋め込まず中間的な要約項目を生成する

6. **チェックリストの生成** - TEMPLATE_CONTENT を構造テンプレートとして使い、「要件のためのユニットテスト」を作成する:
   - `FEATURE_DIR/checklists/` ディレクトリが存在しなければ作成する
   - 一意なチェックリストのファイル名を生成する:
     - ドメインに基づく短く説明的な名前を使う（例: `ux.md`、`api.md`、`security.md`）
     - 形式: `[domain].md`
   - ファイルの扱い:
     - ファイルが存在しない場合: 新規ファイルを作成し、CHK001 から項目を採番する
     - ファイルが存在する場合: 既存ファイルに新しい項目を追記し、最後の CHK ID から続ける（例: 最後の項目が CHK015 なら新しい項目は CHK016 から）
   - 既存のチェックリスト内容を削除または置換してはならない — 常に保持して追記する
   - 新たに生成した項目はすべて未チェック（`[ ]`）のままにする。チェックボックスの状態はレビュアーのものである

   **中核原則 - 実装ではなく要件をテストする**:
   すべてのチェック項目は、要件そのものを次の観点で**必ず**評価すること:
   - **完全性**: 必要な要件がすべて存在するか?
   - **明確さ**: 要件は曖昧でなく具体的か?
   - **一貫性**: 要件同士が整合しているか?
   - **測定可能性**: 要件を客観的に検証できるか?
   - **網羅性**: すべてのシナリオ/エッジケースが扱われているか?

   **カテゴリ構成** - 要件品質の観点で項目をグループ化する:
   - **要件の完全性**（必要な要件がすべて文書化されているか?）
   - **要件の明確さ**（要件は具体的で曖昧でないか?）
   - **要件の一貫性**（要件は矛盾なく整合しているか?）
   - **受け入れ基準の品質**（成功基準は測定可能か?）
   - **シナリオ網羅性**（すべてのフロー/ケースが扱われているか?）
   - **エッジケース網羅性**（境界条件が定義されているか?）
   - **非機能要件**（パフォーマンス、セキュリティ、アクセシビリティなど — 明記されているか?）
   - **依存関係と前提**（文書化され検証されているか?）
   - **曖昧さと矛盾**（何を明確化する必要があるか?）

   **チェック項目の書き方 - 「英語のためのユニットテスト」**:

   ❌ **誤り**（実装をテストしている）:
   - 「ランディングページに3つのエピソードカードが表示されることを検証する」
   - 「デスクトップでホバー状態が動作することをテストする」
   - 「ロゴのクリックでホームに遷移することを確認する」

   ✅ **正しい**（要件品質をテストしている）:
   - 「注目エピソードの正確な数とレイアウトが明記されているか?」[Completeness]
   - 「『目立つ表示』は具体的なサイズ/配置で定量化されているか?」[Clarity]
   - 「ホバー状態の要件はすべてのインタラクティブ要素で一貫しているか?」[Consistency]
   - 「すべてのインタラクティブ UI に対してキーボードナビゲーション要件が定義されているか?」[Coverage]
   - 「ロゴ画像の読み込みに失敗した場合のフォールバック挙動が明記されているか?」[Edge Cases]
   - 「非同期のエピソードデータに対するローディング状態が定義されているか?」[Completeness]
   - 「競合する UI 要素の視覚的階層を仕様書は定義しているか?」[Clarity]

   **項目の構造**:
   各項目は次のパターンに従うこと:
   - 要件品質について問う疑問形
   - 仕様書/計画に何が書かれているか（書かれていないか）に焦点を当てる
   - 品質観点を角括弧に含める [Completeness/Clarity/Consistency/etc.]
   - 既存要件を確認する場合は仕様書のセクション `[Spec §X.Y]` を参照する
   - 欠落した要件を確認する場合は `[Gap]` マーカーを使う

   **品質観点別の例**:

   完全性:
   - 「すべての API 障害モードに対するエラー処理要件が定義されているか? [Gap]」
   - 「すべてのインタラクティブ要素に対するアクセシビリティ要件が明記されているか? [Completeness]」
   - 「レスポンシブレイアウトのモバイルブレークポイント要件が定義されているか? [Gap]」

   明確さ:
   - 「『高速な読み込み』は具体的な時間しきい値で定量化されているか? [Clarity, Spec §NFR-2]」
   - 「『関連エピソード』の選定基準は明示的に定義されているか? [Clarity, Spec §FR-5]」
   - 「『目立つ』は測定可能な視覚的特性で定義されているか? [Ambiguity, Spec §FR-4]」

   一貫性:
   - 「ナビゲーション要件はすべてのページで整合しているか? [Consistency, Spec §FR-10]」
   - 「カードコンポーネントの要件はランディングページと詳細ページで一貫しているか? [Consistency]」

   網羅性:
   - 「ゼロ件状態のシナリオ（エピソードなし）に対する要件が定義されているか? [Coverage, Edge Case]」
   - 「同時ユーザー操作のシナリオが扱われているか? [Coverage, Gap]」
   - 「部分的なデータ読み込み失敗に対する要件が明記されているか? [Coverage, Exception Flow]」

   測定可能性:
   - 「視覚的階層の要件は測定可能/テスト可能か? [Acceptance Criteria, Spec §FR-1]」
   - 「『バランスの取れた視覚的重み』を客観的に検証できるか? [Measurability, Spec §FR-2]」

   **シナリオ分類と網羅性**（要件品質に焦点）:
   - 次のシナリオに対する要件が存在するか確認する: 主要、代替、例外/エラー、復旧、非機能
   - 各シナリオクラスについて次を問う: 「[シナリオ種別] の要件は完全で、明確で、一貫しているか?」
   - シナリオクラスが欠けている場合: 「[シナリオ種別] の要件は意図的に除外されているのか、それとも欠落しているのか? [Gap]」
   - 状態の変更が発生する場合は回復性/ロールバックを含める: 「マイグレーション失敗時のロールバック要件が定義されているか? [Gap]」

   **トレーサビリティ要件**:
   - 最低ライン: 項目の 80% 以上が少なくとも1つのトレーサビリティ参照を含むことが**必須**
   - 各項目は仕様書のセクション `[Spec §X.Y]` を参照するか、マーカー `[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]` を使うこと
   - ID 体系が存在しない場合: 「要件と受け入れ基準の ID 体系が確立されているか? [Traceability]」

   **問題の洗い出しと解消**（要件品質上の問題）:
   要件そのものについて問う:
   - 曖昧さ: 「『高速』という語は具体的な指標で定量化されているか? [Ambiguity, Spec §NFR-1]」
   - 矛盾: 「ナビゲーション要件は §FR-10 と §FR-10a の間で矛盾していないか? [Conflict]」
   - 前提: 「『ポッドキャスト API は常に利用可能』という前提は検証されているか? [Assumption]」
   - 依存関係: 「外部ポッドキャスト API に関する要件は文書化されているか? [Dependency, Gap]」
   - 定義の欠落: 「『視覚的階層』は測定可能な基準で定義されているか? [Gap]」

   **内容の集約**:
   - ソフト上限: 候補項目の生数が 40 を超える場合は、リスク/影響度で優先順位を付ける
   - 同じ要件の側面を確認する準重複項目はマージする
   - 影響の小さいエッジケースが5件を超える場合は、1項目にまとめる: 「エッジケース X、Y、Z は要件で扱われているか? [Coverage]」

   **🚫 絶対禁止** - 以下は要件テストではなく実装テストにしてしまう:
   - ❌ 「検証する」「テストする」「確認する」「チェックする」＋実装挙動、で始まる項目
   - ❌ コード実行、ユーザー操作、システム挙動への言及
   - ❌ 「正しく表示される」「適切に動作する」「期待どおり機能する」
   - ❌ 「クリック」「遷移」「レンダリング」「読み込み」「実行」
   - ❌ テストケース、テスト計画、QA 手順
   - ❌ 実装の詳細（フレームワーク、API、アルゴリズム）

   **✅ 必須パターン** - 以下は要件品質をテストする:
   - ✅ 「[シナリオ] に対する [要件種別] が定義/明記/文書化されているか?」
   - ✅ 「[曖昧な語] は具体的な基準で定量化/明確化されているか?」
   - ✅ 「要件は [セクション A] と [セクション B] の間で一貫しているか?」
   - ✅ 「[要件] を客観的に測定/検証できるか?」
   - ✅ 「[エッジケース/シナリオ] は要件で扱われているか?」
   - ✅ 「仕様書は [欠けている側面] を定義しているか?」

7. **構造の参照**: タイトル、メタセクション、カテゴリ見出し、所有権に関する注記、補足セクション、ID 書式については、`templates/checklist-template.md` の正典テンプレートに従ってチェックリストを生成する。テンプレートが利用できない場合は次を用いる: H1 タイトル、purpose/created のメタ行、`[x]` が要件品質に対するレビュアーの承認を意味することを説明する所有権の注記、`- [ ] CHK### <要件項目>` の行を含む `##` カテゴリセクション（ID は CHK001 から始まり全体で連番）、および `/speckit-implement` はチェックリストの状態を読むがマーカーを変更しないという補足。

8. **報告**: チェックリストファイルの絶対パス、項目数、および今回の実行が新規ファイルを作成したのか既存ファイルに追記したのかを出力する。次を要約する:
   - 選択した重点領域
   - 深さのレベル
   - 実施者/タイミング
   - 取り込んだ、ユーザーが明示した必須項目

**重要**: `/speckit-checklist` コマンドの各呼び出しは、短く説明的なチェックリストファイル名を使い、新規ファイルを作成するか既存ファイルに追記するかのいずれかを行う。これにより次が可能になる:

- 種別の異なる複数のチェックリスト（例: `ux.md`、`test.md`、`security.md`）
- チェックリストの目的が分かる、単純で覚えやすいファイル名
- `checklists/` フォルダ内での識別と移動の容易さ

散らかりを避けるため、説明的な種別名を使い、不要になったチェックリストは片付けること。

## アンチ例: やってはいけないこと

**❌ 誤り - これらは要件ではなく実装をテストしている:**

```markdown
- [ ] CHK001 - ランディングページに3つのエピソードカードが表示されることを検証する [Spec §FR-001]
- [ ] CHK002 - デスクトップでホバー状態が正しく動作することをテストする [Spec §FR-003]
- [ ] CHK003 - ロゴのクリックでホームページに遷移することを確認する [Spec §FR-010]
- [ ] CHK004 - 関連エピソードのセクションに3〜5件表示されることをチェックする [Spec §FR-005]
```

**✅ 正しい - これらは要件品質をテストしている:**

```markdown
- [ ] CHK001 - 注目エピソードの数とレイアウトは明示的に指定されているか? [Completeness, Spec §FR-001]
- [ ] CHK002 - ホバー状態の要件はすべてのインタラクティブ要素で一貫して定義されているか? [Consistency, Spec §FR-003]
- [ ] CHK003 - クリック可能なブランド要素すべてについてナビゲーション要件は明確か? [Clarity, Spec §FR-010]
- [ ] CHK004 - 関連エピソードの選定基準は文書化されているか? [Gap, Spec §FR-005]
- [ ] CHK005 - 非同期のエピソードデータに対するローディング状態の要件が定義されているか? [Gap]
- [ ] CHK006 - 「視覚的階層」の要件を客観的に測定できるか? [Measurability, Spec §FR-001]
```

**主な違い:**

- 誤り: システムが正しく動作するかをテストする
- 正しい: 要件が正しく書かれているかをテストする
- 誤り: 挙動の検証
- 正しい: 要件品質の検証
- 誤り: 「それは X をするか?」
- 正しい: 「X は明確に指定されているか?」

## 実行後チェック

**拡張フックの確認（チェックリスト生成後）**:
プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.after_checklist` キー配下のエントリを探す
- YAML がパースできない、または不正な場合は黙ってスキップしないこと。`.specify/extensions.yml` を読めなかったこと（パーサーのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めてフックが一切チェックされなかったことをユーザーに伝え、その後は通常どおり続行する
- `enabled` が明示的に `false` のフックは除外する。`enabled` フィールドを持たないフックは既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックに `condition` フィールドがない、または null/空の場合は、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    上記ブロックを出力した後、続行する前に実際にフックを**必ず**呼び出し、完了を待つこと。このエージェント/セッションで自分がそのコマンドを実行するのと同じ方法で実行する（呼び出し方は上に示した文字どおりの `{command}` ID とは異なる場合がある。例えば skills モードのエージェントは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
- フックが1つも登録されていない場合、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## 日本語出力ガードレール（Spec Kit 日本語版 / 全コマンド共通）

このセクションは Spec Kit 日本語版が全コマンドに付与する共通の後処理規約である。**省略してはならない。**

### G1. 成果物の記述言語

このコマンドがファイルを生成・更新する場合（`spec.md` / `plan.md` / `tasks.md` / `checklists/*.md` / `.specify/memory/constitution.md` / `research.md` / `data-model.md` / `quickstart.md` / `contracts/` 配下など）、その本文は**日本語**で記述すること。ユーザーへのチャット応答も日本語で行う。

次のものは例外として**英語のまま**維持する。

- ソースコード、シェルコマンド、識別子、型名、ファイルパス、ディレクトリ名、ブランチ名
- `[NEEDS CLARIFICATION: ...]`、`[P]`、`FR-###`、`SC-###`、`NFR-###`、`US1`/`US2`/`US3`、`T001` などの機械可読マーカーおよびID書式
- 業務分析拡張の ID 書式（`BR-###`、`EX-###`）と、ヒアリングシートの ID 書式（`AS-01`、`TB-01`、`R-01`、`E-01`、`Q-01`）
- `**Given**` / `**When**` / `**Then**`（Gherkin 記法）
- 外部ツールやこのコマンド自身が解釈する固定文字列（`EXECUTE_COMMAND:` など）
- 技術用語の原語表記が適切な場合の英単語（API、CI、OAuth など）

ユーザーが英語で指示した場合や、既存の成果物が英語で書かれている場合は、その言語に合わせてよい。それ以外は日本語を既定とする。

### G2. 文字化け検証（書き込み後に必ず実行）

ファイルの書き込み・編集が完了したら、**毎回**次の手順を実行する。

1. 書き込んだファイルを読み直す。
2. 次のいずれかに該当しないか確認する。
   - 置換文字 U+FFFD（いわゆる「黒ひし形に疑問符」の記号）が含まれる
   - mojibake パターンが含まれる（`ã`, `â`, `ï¿½`, `ãƒ`, `æ–‡`, `ð` で始まる不自然な連なりなど）
   - 日本語で書くべき本文が英語のままになっている（G1 の例外を除く）
   - 見出しや表が壊れている（列数の不一致、閉じていないコードフェンス）
3. 該当した場合は、そのファイルを **UTF-8 (BOMなし)** で**丸ごと書き直す**。差分パッチや部分置換で済ませない。
4. 書き直しを2回試しても解消しない場合は、作業を中断し、ユーザーに次を報告する。

   > 文字化けが解消しません。エディタまたは端末のエンコーディング設定（UTF-8 / コードページ）を確認してください。Windows PowerShell の場合は `$PSDefaultParameterValues['*:Encoding']='utf8'` と `chcp 65001` を確認してください。

### G3. 用語の統一

同一プロジェクト内では訳語を揺らさない。既に `spec.md` や `constitution.md` で使われている訳語があれば、それに合わせる。判断に迷う場合は英語を併記する（例: 受け入れシナリオ (acceptance scenario)）。
