## ユーザー入力

```text
$ARGUMENTS
```

続行する前に、ユーザー入力（空でない場合）を**必ず**考慮すること。

## 実行前チェック

**拡張フックの確認（分析前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合はそれを読み込み、`hooks.before_analyze` キー配下のエントリを探す
- YAML がパースできない、または不正な場合、黙ってスキップしてはならない。`.specify/extensions.yml` を読み込めなかったこと（パーサーのエラーを含める）と、そこに登録された必須（`optional: false`）フックを含めていかなるフックも確認されなかったことをユーザーに伝え、その後は通常どおり続行する
- `enabled` が明示的に `false` のフックは除外する。`enabled` フィールドを持たないフックは、既定で有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックが `condition` フィールドを持たない、または null／空の場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:
  - **任意フック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Goal.
    ```
    上記のブロックを出力したあと、実際にフックを呼び出し、その完了を待ってから続行しなければならない。このエージェント／セッションで自分がそのコマンドを実行するのと同じ方法で実行すること（呼び出し方は上に示した `{command}` の ID そのものとは異なることがある。例えばスキルモードのエージェントでは `/skill:speckit-...` または `$speckit-...` として実行する）。ブロックを出力しただけではフックは実行されない。
- フックが登録されていない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## 目的

実装前に、3つの中核成果物（`spec.md`、`plan.md`、`tasks.md`）をまたぐ不整合・重複・曖昧さ・記述不足の項目を洗い出す。このコマンドは、`/speckit-tasks` が完全な `tasks.md` を正常に生成したあとにのみ実行しなければならない。

## 動作上の制約

**厳密に読み取り専用**: いかなるファイルも変更**しない**こと。構造化された分析レポートを出力する。任意の是正計画を提示する（後続の編集コマンドを手動で呼び出す前に、ユーザーが明示的に承認しなければならない）。

**憲法の権威**: プロジェクト憲法（`/memory/constitution.md`）は、この分析スコープ内では**交渉の余地がない**。憲法との衝突は自動的に CRITICAL であり、原則の希釈・再解釈・黙殺ではなく、仕様書・計画・タスクの側の調整を要する。原則そのものを変更する必要がある場合は、`/speckit-analyze` の外で、独立した明示的な憲法更新として行わなければならない。

## 実行ステップ

### 1. 分析コンテキストの初期化

リポジトリルートから `{SCRIPT}` を一度実行し、JSON をパースして FEATURE_DIR と AVAILABLE_DOCS を取得する。絶対パスを導出する:

- SPEC = FEATURE_DIR/spec.md
- PLAN = FEATURE_DIR/plan.md
- TASKS = FEATURE_DIR/tasks.md

必要なファイルが1つでも欠けている場合は、エラーメッセージを出して中止する（不足している前提コマンドを実行するようユーザーに指示する）。
"I'm Groot" のように引数にシングルクォートが含まれる場合は、エスケープ構文を使う。例: 'I'\''m Groot'（可能ならダブルクォートでもよい: "I'm Groot"）。

### 2. 成果物の読み込み（漸進的開示）

各成果物から、必要最小限のコンテキストのみを読み込む:

**spec.md から:**

- 概要／コンテキスト
- 機能要件
- 成功基準（測定可能な成果 — 例: 性能、セキュリティ、可用性、ユーザーの成功、ビジネスインパクト）
- ユーザーストーリー
- エッジケース（存在する場合）

**plan.md から:**

- アーキテクチャ／スタックの選択
- データモデルへの参照
- フェーズ
- 技術的制約

**tasks.md から:**

- タスクID
- 説明
- フェーズのグルーピング
- 並列マーカー [P]
- 参照されているファイルパス

**憲法から:**

- 原則の検証のために `/memory/constitution.md` を読み込む

### 3. 意味モデルの構築

内部表現を作成する（生の成果物を出力に含めないこと）:

- **要件インベントリ**: 各機能要件（FR-###）および各成功基準（SC-###）について、安定したキーを記録する。明示的な FR-/SC- 識別子がある場合はそれを主キーとして使い、可読性のために命令句のスラッグを併せて導出してもよい（例: "User can upload file" → `user-can-upload-file`）。成功基準は、構築作業を伴う項目のみを含め（例: 負荷試験の基盤、セキュリティ監査ツール）、ローンチ後の成果指標やビジネスKPI（例: 「サポートチケットを50%削減」）は除外する。
- **ユーザーストーリー／アクションのインベントリ**: 受け入れ基準を伴う個別のユーザー操作
- **タスク網羅性のマッピング**: 各タスクを1つ以上の要件またはストーリーに対応付ける（キーワードによる推論、あるいは ID やキーフレーズなどの明示的な参照パターンによる）
- **憲法ルールセット**: 原則名と MUST／SHOULD の規範的記述を抽出する

### 4. 検出パス（トークン効率の高い分析）

シグナルの強い指摘に集中する。指摘は合計50件までとし、残りはオーバーフロー要約にまとめる。

#### A. 重複の検出

- ほぼ重複している要件を特定する
- 統合のために、品質の低い表現の方に印を付ける

#### B. 曖昧さの検出

- 測定可能な基準を欠いた曖昧な形容詞（高速、スケーラブル、セキュア、直感的、堅牢）にフラグを立てる
- 未解決のプレースホルダ（TODO、TKTK、???、`<placeholder>` など）にフラグを立てる

#### C. 記述不足

- 動詞はあるが目的語または測定可能な成果を欠く要件
- 受け入れ基準との対応が欠けているユーザーストーリー
- spec/plan で定義されていないファイルやコンポーネントを参照しているタスク

#### D. 憲法との整合

- MUST 原則と衝突する要件または計画要素
- 憲法が義務付けるセクションまたは品質ゲートの欠落

#### E. 網羅性のギャップ

- 対応するタスクが1つもない要件
- 対応する要件／ストーリーにマッピングされていないタスク
- 構築作業を要する成功基準（性能、セキュリティ、可用性）がタスクに反映されていない

#### F. 不整合

- 用語のぶれ（同じ概念がファイル間で異なる名前で呼ばれている）
- plan で参照されているが spec に存在しないデータエンティティ（またはその逆）
- タスク順序の矛盾（例: 依存関係の注記なしに、基盤セットアップのタスクより前に統合タスクが置かれている）
- 衝突する要件（例: 一方が Next.js を要求し、他方が Vue を指定している）

### 5. 深刻度の割り当て

指摘の優先順位付けには、次のヒューリスティクスを使う:

- **CRITICAL**: 憲法の MUST に違反、中核となる仕様成果物が欠落、または基本機能をブロックする網羅性ゼロの要件
- **HIGH**: 重複または衝突する要件、曖昧なセキュリティ／性能属性、テスト不能な受け入れ基準
- **MEDIUM**: 用語のぶれ、非機能要件に対するタスク網羅性の欠落、記述不足のエッジケース
- **LOW**: スタイル／表現の改善、実行順序に影響しない軽微な冗長性

### 6. コンパクトな分析レポートの生成

次の構造を持つ Markdown レポートを出力する（ファイルへの書き込みは行わない）:

## 仕様分析レポート

| ID | カテゴリ | 深刻度 | 該当箇所 | 要約 | 推奨対応 |
|----|----------|--------|----------|------|----------|
| A1 | 重複 | HIGH | spec.md:L120-134 | 類似した要件が2件 ... | 表現を統合し、より明確な方を残す |

（指摘ごとに1行追加する。カテゴリの頭文字を接頭辞とする安定した ID を生成すること。）

**網羅性サマリ表:**

| 要件キー | タスクあり？ | タスクID | 備考 |
|----------|--------------|----------|------|

**憲法との整合上の問題:**（ある場合）

**マッピングされていないタスク:**（ある場合）

**メトリクス:**

- 要件の総数
- タスクの総数
- 網羅率 %（タスクが1件以上ある要件）
- 曖昧さの件数
- 重複の件数
- Critical 問題の件数

### 7. 次のアクションの提示

レポートの末尾に、簡潔な「次のアクション」ブロックを出力する:

- CRITICAL の問題がある場合: `/speckit-implement` の前に解消することを推奨する
- LOW/MEDIUM のみの場合: ユーザーは続行してよいが、改善提案を提示する
- 明示的なコマンドの提案を示す。例: 「/speckit-specify を実行して洗練する」「/speckit-plan を実行してアーキテクチャを調整する」「tasks.md を手動で編集して 'performance-metrics' の網羅性を追加する」

### 8. 是正の提案

ユーザーに尋ねる: 「上位N件の問題について、具体的な是正案を提示しましょうか？」（自動的に適用しては**ならない**。）

- 実行可能な各フックについて、その `optional` フラグに応じて以下を出力する:

## 動作原則

### コンテキスト効率

- **シグナルの強い最小限のトークン**: 網羅的な文書化ではなく、実行可能な指摘に集中する
- **漸進的開示**: 成果物は段階的に読み込む。全内容を分析に流し込まない
- **トークン効率の高い出力**: 指摘表は50行までに制限し、超過分は要約する
- **決定的な結果**: 変更なしで再実行した場合、一貫した ID と件数が生成されること

### 分析ガイドライン

- **ファイルを決して変更しない**（これは読み取り専用の分析である）
- **欠落しているセクションを決して捏造しない**（存在しない場合は、その事実を正確に報告する）
- **憲法違反を最優先する**（これらは常に CRITICAL である）
- **網羅的な規則より例示を使う**（汎用的なパターンではなく、具体的な事例を引用する）
- **問題ゼロの場合も丁寧に報告する**（網羅性の統計を含む成功レポートを出力する）

## 業務分析拡張（Spec Kit 日本語版）

このセクションは、業務システムの要件分析を補強するために Spec Kit 日本語版が追加した規約である。spec.md に `## 業務要件` セクションがある場合に適用する。無い場合は本セクションを無視する。

### B1. 読み込みの追加

実行ステップ2の「spec.md から」に、次を加える。

- 業務要件 > 権限（ロールと操作）
- 業務要件 > 業務ルール（BR-###）
- 業務要件 > 業務上の例外処理（EX-###）
- 業務要件 > 用語集

### B2. 意味モデルへの追加

実行ステップ3の要件インベントリに、BR-### と EX-### を FR-### と同じ扱いで加える。各 BR / EX に書かれた「関連: FR-###」も、タスク網羅性のマッピングの手がかりにする。

### B3. 検出パスへの追加

- **C. 記述不足**:
  - 数値・条件・対象者のいずれも無い BR-###（「適切に」「原則として」だけで、例外の条件が書かれていないもの）
  - 関連する FR-### もシナリオも無い BR-### / EX-###
  - 追跡性: 出典に「推定」を含む BR-### / EX-###、または 前提 で「慣習のため要確認」とされた BR-### に基づく実装タスクがある場合は、業務担当者の確認を促す指摘（MEDIUM）を出す
- **E. 網羅性のギャップ**:
  - 対応するタスク（実装またはテスト）が無い BR-### / EX-###
  - 権限表で「×」（できない）または「△」（条件付き）の操作に対応する、認可の実装タスクが無い
  - tasks.md にテストタスクがある場合に限り、「×」「△」の操作が許可されないことを確認するテストタスクが無い
- **F. 不整合**: 権限表と plan.md／tasks.md の認可の扱いの食い違い。権限表のロール名とユーザーストーリーのアクター名の不一致。用語集で「使わない言い方」とされた語が spec／plan／tasks で使われている。

### B4. レポートへの追加

- 網羅性サマリ表の要件キーに BR-### と EX-### を含める。
- メトリクスに「業務ルール・例外の総数」「うちタスクがあるもの」「出典に推定を含む件数」「慣習のため要確認の件数」を加える。

## 日本語出力ガードレール（Spec Kit 日本語版 / 全コマンド共通）

このセクションは Spec Kit 日本語版が全コマンドに付与する共通の後処理規約である。**省略してはならない。**

### G1. 成果物の記述言語

このコマンドがファイルを生成・更新する場合（`spec.md` / `plan.md` / `tasks.md` / `checklists/*.md` / `.specify/memory/constitution.md` / `research.md` / `data-model.md` / `quickstart.md` / `contracts/` 配下など）、その本文は**日本語**で記述すること。ユーザーへのチャット応答も日本語で行う。

次のものは例外として**英語のまま**維持する。

- ソースコード、シェルコマンド、識別子、型名、ファイルパス、ディレクトリ名、ブランチ名
- `[NEEDS CLARIFICATION: ...]`、`[P]`、`FR-###`、`SC-###`、`NFR-###`、`US1`/`US2`/`US3`、`T001` などの機械可読マーカーおよびID書式
- 業務分析拡張の ID 書式（`BR-###`、`EX-###`）と、ヒアリングシートの ID 書式（`AS-01`、`TB-01`、`R-01`、`E-01`、`Q-01`）
- `**Given**` / `**When**` / `**Then**`（Gherkin 記法）
- 外部ツールやこのコマンド自身が解釈する固定文字列（`EXECUTE_COMMAND:` など）
- 技術用語の原語表記が適切な場合の英単語（API、CI、OAuth など）

ユーザーが英語で指示した場合や、既存の成果物が英語で書かれている場合は、その言語に合わせてよい。それ以外は日本語を既定とする。

### G2. 文字化け検証（書き込み後に必ず実行）

ファイルの書き込み・編集が完了したら、**毎回**次の手順を実行する。

1. 書き込んだファイルを読み直す。
2. 次のいずれかに該当しないか確認する。
   - 置換文字 U+FFFD（いわゆる「黒ひし形に疑問符」の記号）が含まれる
   - mojibake パターンが含まれる（`ã`, `â`, `ï¿½`, `ãƒ`, `æ–‡`, `ð` で始まる不自然な連なりなど）
   - 日本語で書くべき本文が英語のままになっている（G1 の例外を除く）
   - 見出しや表が壊れている（列数の不一致、閉じていないコードフェンス）
3. 該当した場合は、そのファイルを **UTF-8 (BOMなし)** で**丸ごと書き直す**。差分パッチや部分置換で済ませない。
4. 書き直しを2回試しても解消しない場合は、作業を中断し、ユーザーに次を報告する。

   > 文字化けが解消しません。エディタまたは端末のエンコーディング設定（UTF-8 / コードページ）を確認してください。Windows PowerShell の場合は `$PSDefaultParameterValues['*:Encoding']='utf8'` と `chcp 65001` を確認してください。

### G3. 用語の統一

同一プロジェクト内では訳語を揺らさない。既に `spec.md` や `constitution.md` で使われている訳語があれば、それに合わせる。判断に迷う場合は英語を併記する（例: 受け入れシナリオ (acceptance scenario)）。
