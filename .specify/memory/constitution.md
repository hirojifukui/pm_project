# 旅費精算システム 憲法

## 中核原則

### I. 日本語ユーザー体験 (NON-NEGOTIABLE)

利用者向けに表示されるあらゆる文字列（画面ラベル、ボタン、入力項目名、ヘルプ、
バリデーションメッセージ、エラーメッセージ、確認ダイアログ、通知メール、PDF、CSV の
ヘッダ）は日本語で記述しなければならない (MUST)。英数字や記号は、業務用語として
日本語化できない固有名詞（例: CSV、PDF、ID）に限って用いてよい (MAY)。
技術用語（例外、スタックトレース、HTTP ステータス、SQL エラー、null、undefined 等）を
利用者画面にそのまま出してはならない (MUST NOT)。例外発生時は、業務担当者が次に
取るべき行動が分かる日本語メッセージへ必ず変換すること (MUST)。

**根拠**: 利用者はプログラミング経験のない業務担当者であり、英語の技術用語や
生のシステム例外を提示されても次の行動を判断できず、問い合わせ対応や差戻しの
コストが膨らむ。

### II. 業務担当者ファーストの操作性

本システムの一次利用者はプログラミング経験のない業務担当者であることを前提とする
(MUST)。したがって次を遵守する。

- 入力画面は、業務ヒアリングシート (`docs/requirements/`) の用語をそのまま採用し、
  システム内部の識別子（主キー、内部コード）を一次ラベルとして露出させてはならない
  (MUST NOT)。
- 業務担当者が実行する操作には、確認・取消・修正の経路を必ず用意する (MUST)。
  不可逆な操作（確定、送信、削除）は、確認ダイアログで対象の件数と内容を要約してから
  実行する (MUST)。
- バリデーションは、どの項目のどの値が規程のどの条件に反しているかを特定できる
  メッセージで返す (MUST)。「不正な値です」等の無内容メッセージを単独で用いてはならない
  (MUST NOT)。
- 利用者が設定ファイル、CLI、環境変数、SQL を触らずに完結する UI 操作だけで、
  申請・承認・差戻し・精算・CSV 出力・履歴参照のすべてが可能であること (MUST)。

**根拠**: 業務担当者が運用の主体であり、技術者による介助が常に得られる前提では
設計できない。UI 操作で完結しないと、現場で業務が止まる。

### III. 業務ルールはテストで検証 (NON-NEGOTIABLE)

業務ルール（旅費規程、承認権限、上限金額、差戻し条件、締切、CSV 出力ルール、
期間制限、重複チェック、丸め処理、消費税の扱い等）には、必ず実行可能な自動テストを
対応付けなければならない (MUST)。業務ルールの追加・変更・削除は、次の順序で行う
(MUST)。

1. 業務ヒアリングシートまたは仕様書 (`spec.md`) に業務要件 ID（例: `BR-###`）として
   明記する。
2. 当該 ID を参照する受け入れシナリオ (acceptance scenario) を `**Given** / **When** /
   **Then**` 形式で定義する。
3. 当該シナリオを失敗（Red）するテストとしてコード化し、合意を得てから実装する。
4. 実装でテストを緑（Green）にし、リファクタリングで維持する。

テストが存在しない業務ルールを本番相当環境に投入してはならない (MUST NOT)。
手動確認で代替してはならない (MUST NOT)。業務ルールの境界値（上限金額ちょうど、
期限最終日、ゼロ件、最大件数、消費税端数など）は、必ずテストケースを用意する
(MUST)。

**根拠**: 旅費規程違反による差戻しは現状でも約2割発生しており、ルールの誤実装は
金銭的な過不足と再承認の負担を生む。業務ルールの正しさは「読めば分かる」ではなく
「テストが通る」で担保する。

### IV. 個人情報の露出禁止 (NON-NEGOTIABLE)

個人情報（氏名、社員番号、メールアドレス、口座情報、金額、出張先、同行者、
領収書画像、押印画像など、申請者または第三者を特定し得る情報）は、業務上必要な
UI 画面と、認可された利用者が自分の権限範囲で見るときにだけ表示する (MUST)。
次の経路に出してはならない (MUST NOT)。

- アプリケーションログ、アクセスログ、監査ログ、エラーログ、スタックトレース
- URL のクエリ文字列、パスパラメータ、リファラ
- 外部サービス（検索エンジン、分析ツール、クラッシュレポート、LLM API、翻訳 API 等）
  への送信ペイロード
- 開発環境・テスト環境・デモ環境（実データは入れない。マスクまたは合成データを使う）
- CSV・PDF など成果物のうち、受領者の権限範囲を越える列・項目

ログに記録する場合でも、申請 ID のような内部識別子に留め、識別子から個人情報への
解決はアクセス制御されたクエリ経由でのみ可能とする (MUST)。例外・障害調査で
個人情報を参照する必要がある場合は、閲覧記録を監査可能な形で残す (MUST)。

**根拠**: 個人情報の意図せぬ流出は、法令・社内規程・被害者への説明責任のいずれにも
抵触する。ログや URL のような「技術者だけが見ている」と誤認されがちな経路で
最も漏れる。

### V. 仕様駆動開発（Spec Kit 日本語版の遵守）

本プロジェクトは Spec Kit 日本語版のワークフローに従う (MUST)。

- 業務要件の一次情報源は `docs/requirements/` 配下のヒアリングシートとする (MUST)。
- 機能ごとに `specs/<feature>/` の下で `spec.md` → `plan.md` → `tasks.md` の順に
  作成し、各段階で合意を得てから次へ進む (MUST)。
- 仕様書・計画・タスク・チェックリスト・憲法は日本語で記述する (MUST)。
  機械可読マーカー（`FR-###`、`BR-###`、`[NEEDS CLARIFICATION: ...]`、
  `**Given** / **When** / **Then**` 等）は英語のまま維持する (MUST)。
- 業務ルールを導入・変更する際は、ヒアリングシートの該当 ID を仕様書に出典として
  引用する (MUST)。
- 仕様書に `[NEEDS CLARIFICATION: ...]` が残ったまま `plan` / `tasks` /
  `implement` へ進んではならない (MUST NOT)。

**根拠**: 業務担当者と開発者の往復コストを下げ、合意の軌跡を文書化するために、
仕様 → 計画 → タスク → 実装の一方向フローを維持する。合意なき実装は後工程で
やり直しになる。

## 追加の制約・非機能要件

- 画面と帳票の既定ロケールは `ja-JP`、既定タイムゾーンは `Asia/Tokyo` とする
  (MUST)。日付は `YYYY-MM-DD` で表示・保存し、CSV・PDF でも同形式を基本とする
  (MUST)。
- 金額は円単位の整数で保持し、計算の途中で浮動小数点に落としてはならない
  (MUST NOT)。消費税や日当上限の丸めは、業務要件に明記したルール（切り捨て／
  四捨五入／切り上げ）に従って一箇所で行う (MUST)。
- 認可: 自分の申請、自分が承認者となる申請、経理担当として確定可能な申請以外は
  一覧・詳細のいずれにも表示しない (MUST)。ロール逸脱時は 403 相当として扱い、
  利用者には「権限がありません」と日本語で返す (MUST)。
- 監査: 申請・承認・差戻し・確定・取消・個人情報参照の各イベントは、誰が・いつ・
  どの対象に対して行ったかを追跡可能な形で記録する (MUST)。
- 保守: 利用者が理解可能な単位（画面、業務ルール、CSV レイアウト）ごとに
  バージョンを管理し、互換性のない変更には移行手順を添える (MUST)。

## 開発ワークフローと品質ゲート

- すべての Pull Request は、次を満たしてからマージ可能とする (MUST)。
  1. 対応する仕様書・計画・タスクが更新され、`[NEEDS CLARIFICATION: ...]` が
     残っていない。
  2. 変更された業務ルールごとに、追加または更新された自動テストが存在し、CI で
     通過している。
  3. 個人情報の新規保存・新規出力経路が増える場合は、原則 IV の遵守を
     レビューアが確認している。
  4. 画面またはメッセージの変更がある場合は、文言が原則 I・II を満たすことを
     業務側レビューアが確認している。
- レビューは、最低1名の技術レビューアと、業務ルール・UI 文言に影響する変更に
  ついては1名以上の業務レビューア（経理担当・所属長代理など）の合意を要する
  (MUST)。
- CI は、業務ルールテスト・ユニットテスト・結合テスト・個人情報の静的スキャン
  （ログ出力に PII が混ざらないかの検査）を含む (MUST)。失敗した状態での
  マージを許容してはならない (MUST NOT)。
- 本憲法に抵触する実装・運用は、理由と期限付きの例外として `specs/<feature>/`
  内で明示する (MUST)。暗黙の例外は認めない (MUST NOT)。

## ガバナンス

本憲法は、本プロジェクトにおける他のあらゆる慣行・暗黙知・口頭合意に優先する
(MUST)。既存のドキュメントと矛盾する場合は本憲法を正とする (MUST)。

- 改定提案は `/speckit-constitution` コマンドまたは等価な PR で行い、変更理由、
  影響範囲、移行手順を明記する (MUST)。
- バージョニングはセマンティックバージョニングに従う (MUST)。
  - MAJOR: 既存原則の削除・再定義、ガバナンス構造の後方非互換な変更。
  - MINOR: 原則・セクションの追加、または運用ルールの実質的な拡充。
  - PATCH: 文言調整、誤字修正、意味を変えない明確化。
- すべての Pull Request レビューで、本憲法との整合を確認する (MUST)。整合しない
  場合は、本憲法の改定または変更の見直しのいずれかを行う (MUST)。
- 本憲法への準拠が疑わしい設計判断（例: 性能のための個人情報のログ出力、
  テスト省略）は、暗黙に許容してはならない (MUST NOT)。例外は書面化し、
  期限と再評価日を設ける (MUST)。
- 本憲法と関連テンプレートの運用ガイダンスは、`.specify/templates/` および
  `.claude/skills/speckit-*` を参照する。
