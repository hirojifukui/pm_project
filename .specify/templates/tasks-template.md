# タスク: [機能名]

**入力**: `/specs/[###-feature-name]/` の設計ドキュメント

**前提条件**: plan.md（必須）、spec.md（ユーザーストーリーのために必須）、research.md、data-model.md、contracts/

**テスト**: 以下の例にはテストタスクを含めている。テストは任意であり、機能仕様書で明示的に要求された場合のみ含めること。

**構成**: タスクはユーザーストーリー単位でグループ化し、各ストーリーを独立して実装・テストできるようにする。

## 形式: `[ID] [P?] [Story] 説明`

- **[P]**: 並列実行可能（別ファイル、依存なし）
- **[Story]**: このタスクが属するユーザーストーリー（例: US1, US2, US3）
- 説明には正確なファイルパスを記載すること

## パス規約

- **単一プロジェクト**: リポジトリルート直下の `src/`, `tests/`
- **Webアプリ**: `backend/src/`, `frontend/src/`
- **モバイル**: `api/src/`, `ios/src/` または `android/src/`
- 以下に示すパスは単一プロジェクトを前提とする。plan.md の構成に合わせて調整すること

## 依存関係と実行順序

### フェーズ間の依存

- **セットアップ（フェーズ1）**: 依存なし — ただちに開始できる
- **基盤構築（フェーズ2）**: セットアップの完了に依存 — すべてのユーザーストーリーをブロックする
- **ユーザーストーリー（フェーズ3以降）**: すべて基盤構築フェーズの完了に依存
  - その後、ユーザーストーリーは並列に進められる（人員が確保できる場合）
  - あるいは優先度順に逐次進める（P1 → P2 → P3）
- **仕上げ（最終フェーズ）**: 対象とするすべてのユーザーストーリーの完了に依存

### ユーザーストーリー間の依存

- **ユーザーストーリー1 (P1)**: 基盤構築（フェーズ2）の後に開始可能 — 他ストーリーへの依存なし
- **ユーザーストーリー2 (P2)**: 基盤構築（フェーズ2）の後に開始可能 — US1 と統合する場合もあるが、独立してテスト可能であるべき
- **ユーザーストーリー3 (P3)**: 基盤構築（フェーズ2）の後に開始可能 — US1/US2 と統合する場合もあるが、独立してテスト可能であるべき

### 各ユーザーストーリー内の依存

- テスト（含める場合）は実装前に**必ず**書き、失敗させること
- モデルはサービスより先
- サービスはエンドポイントより先
- 中核実装は統合より先
- 次の優先度に移る前にストーリーを完了させること

### 並列実行の機会

- [P] が付いたセットアップタスクはすべて並列実行できる
- [P] が付いた基盤構築タスクはすべて並列実行できる（フェーズ2内）
- 基盤構築フェーズが完了すれば、すべてのユーザーストーリーを並列に開始できる（チームの余力が許す場合）
- あるユーザーストーリーの [P] が付いたテストはすべて並列実行できる
- ストーリー内の [P] が付いたモデルは並列実行できる
- 異なるユーザーストーリーは、異なるメンバーが並行して作業できる

## 実装戦略

### MVPファースト（ユーザーストーリー1のみ）

1. フェーズ1: セットアップを完了する
2. フェーズ2: 基盤構築を完了する（重要 — すべてのストーリーをブロックする）
3. フェーズ3: ユーザーストーリー1 を完了する
4. **停止して検証する**: ユーザーストーリー1 を独立してテストする
5. 準備が整っていればデプロイ／デモする

### 漸進的デリバリー

1. セットアップ＋基盤構築を完了 → 基盤が整う
2. ユーザーストーリー1 を追加 → 独立してテスト → デプロイ／デモ（MVP!）
3. ユーザーストーリー2 を追加 → 独立してテスト → デプロイ／デモ
4. ユーザーストーリー3 を追加 → 独立してテスト → デプロイ／デモ
5. 各ストーリーは、既存のストーリーを壊すことなく価値を追加する

### チーム並列戦略

複数の開発者がいる場合:

1. チーム全体でセットアップ＋基盤構築を完了する
2. 基盤構築が完了したら:
   - 開発者A: ユーザーストーリー1
   - 開発者B: ユーザーストーリー2
   - 開発者C: ユーザーストーリー3
3. 各ストーリーは独立して完了・統合する

## 補足

- [P] タスク = 別ファイル、依存なし
- [Story] ラベルは、トレーサビリティのためタスクを特定のユーザーストーリーに紐付ける
- 各ユーザーストーリーは独立して完了・テストできること
- 実装前にテストが失敗することを確認する
- タスクごと、または論理的なまとまりごとにコミットする
- 任意のチェックポイントで停止し、ストーリーを独立して検証する
- 避けること: 曖昧なタスク、同一ファイルの競合、独立性を壊すストーリー間の依存
